# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Plugin purpose

`ok` is the suite's front door and sole administrator. It carries one skill family as payload, `families/ok-planner`: a self-contained directory of skills (`/audit` and `/document` among them), agent profiles, templates, rules files, standards, support scripts (the lint, `catalog-toc`, `run-tag`, and `port-block` among them), hooks, and the two administration files. Everything the suite vendors into a project comes from that family; the plugin carries no layer of its own. It ships one skill, `/ok`, that is the whole administration process: install, converge, repair. `/ok` updates the installed user-scoped plugins, discovers whether the project integrates ok-planner by the integration contract's filesystem markers (the planner's estate, or a documented pre-migration marker), offers to bootstrap it in one consent question where every marker is absent, then administers it by driving its two conventional administration files from the payload: the deterministic converge core at `admin/converge` (diagnose / converge / wire-hooks `<group>` / wire-env / resolve) and the administration document at `admin/ADMINISTRATION.md` for the judgment the core cannot encode. Consent is reserved for genuine collisions, non-suite-owned content, and settings transcription — the hook groups and the task-tools env entry; the suite's own retired layouts migrate under converge. Each item the core cannot settle alone is a `CLEANUP OFFERED` block whose fix the core's `resolve` mode applies on the owner's yes, from a draft `/ok` writes outside the project where the fix needs the owner's words, so one `/ok` pass ends converged.

A sprint runs in three steps, all ok-planner verbs. `/plan-sprint` plans it with the owner and ends at an approved sprint carrying implementation notes from a code-planning phase. Execution runs on the task tracker: the session reads the sprint and the code, cuts the work into stages — each the smallest change that makes progress toward the completion contract and leaves the tree runnable — and files one build task (`ok-opus`) per stage under the sprint build prompt, naming the files it may touch and the stages it builds on; stages with disjoint files run together. The drain loop drains them: a fresh agent per task, one cached prefix per profile. The session writes `tasks render`'s output into the completion report and edits no file a running task owns. Code complete means every stage's build task closed `done`. Sprint certification (`/converge sprint <path>`) then closes the sprint: one review of the change for completion and regression, the project's checks, a drive of the stories the sprint touches, and a fix-and-verify loop over what they find.

The family is not a plugin: nothing family-scoped installs machine-globally, and consumers meet the family only through its vendored presence in their project. The factoring is the point — everything specific to the family, from converge mechanics to migration judgment, lives in the family's own directory at the contract's two administration files, so a change to what the suite vendors is a change to the family, never to the administrator.

## Constraints

- Never move family knowledge into the administrator. Migration procedures, config walkthroughs, and conflict handling belong in the family's `admin/ADMINISTRATION.md`; deterministic mechanics belong in its `admin/converge`. Discovery markers are documented in `docs/integration-contract.md` — the contract, not this skill, is where the convention lives.
- Never install, vendor, or offer `ok-conduct`. It is user-scoped and personal; the only thing `/ok` does with it is update an already-installed copy.
- Never invoke a family verb through the Skill tool, and never let `/ok` run work-driving verbs (`audit`, `document`, `plan-sprint`, `converge`) — administration only.
- Never run administration from a hook. It is a user action, always.
- Version stamps derive from this plugin's manifest — the suite version. The family carries no manifest of its own; every stamp its machinery writes reads the front-door manifest.
- The `ok` plugin itself materializes no project estate — it has no dot-directory and is never "integrated"; it acts on whatever project it is run in.
