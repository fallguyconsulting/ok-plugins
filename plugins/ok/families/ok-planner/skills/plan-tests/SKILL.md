# Test planning

`/plan-tests` is ok-planner's test planning session: an interactive session with the project owner that produces a **test sprint**. A test sprint is a plan to bring the project's tests in line with what its stories promise: one test per scenario, each scenario a distinct outcome a user or the product sees through a program, for a way a story's implementation gives or refuses its benefit, or a runtime failure the product must survive. Its execution writes, rewrites, and deletes tests, ports legacy tests that enforce a rule on the code's shape, written or inferred, into project checks, fixes the code for each failing test, and rewrites each slow test whose time goes to a waste the testing standard names. Only a test sprint changes a test.

The owner starts it on their own schedule, as `/plan-tests` or as `/plan-tests widen [<story slug> ...]`. A widen run reopens the stories the owner names, or, with no slug, every story an earlier plan's calls left a path out of: their planners add the scenarios the code supports, on any run, one where nothing changed since the stamp included. A test sprint changes no corpus artifact, docspec, or surface intent: a scenario whose fix needs a commitment changed goes to the next `/plan-sprint` as an issue.

The machinery lives beside this body. `core.md` holds the scenario definition, the runtime classes, the planning prompts, and the run prompts. `test-sprint-document.md` holds the test sprint's template. `.claude/skills/_sprint/shared.md` holds the run rules and the archive step the test sprint follows. A `{{TOKEN}}` names the block of that name in one of these files, and resolves only where the token stands alone on its line. The earlier test sprints and their plans under `.ok-planner/history/test-sprints/` are records: the session reads them only through `.ok-planner/bin/tests calls`, which lists the calls the latest plan to plan a story left for it, and `.ok-planner/bin/tests groups --widen`, which reads the same calls.

## 1. Layout

Read the argument: none, or `widen` followed by story slugs. Where it is anything else, answer with the line `/plan-tests [widen [<story slug> ...]]`, and stop. A slug with no story file is refused at step 6, where `tests groups` names it.

`mkdir -p .ok-planner/test-sprints .ok-planner/history/test-sprints`. Estate true-up is the front door's administration (`/ok`).

`.ok-planner/bin/tests`, `.ok-planner/bin/tasks`, `.ok-planner/bin/plumbline`, `.ok-planner/bin/issues`, and the profile `ok-opus` under `.claude/agents/` are required: where one is missing, say that `/ok` materializes it, and stop.

A test sprint under `.ok-planner/test-sprints/` that is not archived is still open: name it, say that it runs with `/goal <its path>` or that the owner archives it first, and stop. One plan stands at a time.

Name the test sprint `YYYY-MM-DD-<slug>`, from `date +%Y-%m-%d` and a slug for what this plan covers, such as `tests` or `legacy-suite`. Every file this session writes sits under `.ok-planner/test-sprints/` and starts with that name.

## 2. The runner

The runner is the project's suite command and its settings, under `testing` in `.ok-planner/config.json`, each required, with no default:

- `run`, the suite command, which runs a list of tests in one run, deciding batching and setup, with the number of workers the list names. It holds `{tests}`, where the tool puts the path of a JSON file, `{"workers": <n>, "tests": [{"path", "name", "resources": [...]}]}`, and `{results}`, where it puts the path of a stream the command writes one line to per test as each finishes, `{"path", "name", "passed": true or false, "seconds": <number>, "output": "<text>"}`, each line within 512 bytes, its output capped to fit. A line names its test by the path and name the scenario list records; a test the stream never reports fails.
- `silence`, the whole seconds with no result after which the tool stops a run.
- `named`, `true` where the suite command runs a test by its name inside its file, `false` where it runs a whole file.
- `leftovers`, a command that prints one JSON object counting each kind of resource a test may leave behind; a project with nothing to count declares `echo {}`.
- `slowest`, how many of the slowest tests each run lists, and so the size of each batch a test sprint's speed review reads.
- `runners`, the project's own test-running commands that `review checks` refuses as a check, an empty list where the project has no runner of its own to name.

Read `testing` in `.ok-planner/config.json`. Count a key as missing where it is absent, and count `run` as missing where `testing` declares the earlier one-test form: a `run` holding `{path}` and no `{tests}`, or a `timeout` key. Where any key is missing, read how the project runs its tests today: its package manifests, its build files, its CI configuration, and the runner's plugins or reporters that write one line per test as each finishes. Propose to the owner, in one prose question, a value for every missing key: the suite command with each placeholder shown and the result line it writes, such as a small script beside the tests that reads the list, runs the tests with the project's runner, and writes one line per test. Where the project has no tests and no runner, propose one that fits its language. On the owner's answer, run `.ok-planner/bin/tests declare` with the flag of each key the owner gave: `--run "<the command>"`, `--silence <seconds>`, `--named <yes | no>`, `--leftovers "<the command>"`, `--slowest <n>`, and `--runners [<command> ...]`. The tool drops an earlier `timeout`. Where every key is declared, ask nothing.

## 3. Window

Run `.ok-planner/bin/tests window --json`. It names the stamp, the status, the files changed since the stamp, the sprints closed since it, the stories changed, the scenarios whose story is gone, the claimed tests a person edited, and the test files no scenario claims. A status of `new` means no stamp: every story is planned from the start, and every test file is a legacy test. Where the status is `current` and the owner asked for no widen run, say that the tests stand where the last test sprint left them, name `/plan-tests widen [<story slug> ...]` as the way to reopen stories, and stop. Where the owner asked for a widen run, go on, whatever the status.

Tell the owner the counts in one line ("12 scenarios recorded; 40 files changed since the stamp; 3 stories changed; 280 legacy test files to sort"). Record the commit: `git rev-parse HEAD`.

## 4. Run the suite once

Where the stamp recorded tests, run them all through the suite command: `.ok-planner/bin/tests run --json`, and write the output to `.ok-planner/test-sprints/<name>-planning-results.json`. The planners read each test's pass or failure, its output's tail, and its seconds, setup and teardown included, there.

## 5. The owner's inputs

Open the planning run: `tasks init <name>-planning --file .ok-planner/test-sprints/<name>-planning.jsonl`, and `tasks agent register ok-opus`. For each of `{{TEST-STORY-PLANNER-PROMPT}}` as `story`, `{{TEST-RUNTIME-PLANNER-PROMPT}}` as `runtime`, `{{TEST-SORT-PROMPT}}` as `sort`, `{{TEST-PROGRAMS-PROMPT}}` as `programs`, `{{TEST-BUDGET-PROMPT}}` as `budget`, `{{TEST-PLANNER-REVIEW-PROMPT}}` as `review`, and `{{TEST-PLAN-WIDE-REVIEW-PROMPT}}` as `plan-review`, in `core.md`, write the block, its transclusions resolved and `[TEST SPRINT PATH]` filled with `.ok-planner/test-sprints/<name>.md`, to `.ok-planner/test-sprints/<name>-planning-<role>.md`, and register it: `tasks prompt register <role> <that path>`. Declare the pools: `tasks config set item_states '{"scope": ["open"], "stories": ["open"], "scenarios": ["open"], "questions": ["open", "answered"], "legacy": ["open"], "calls": ["open"], "controls": ["open"], "budget": ["open"], "limits": ["open"], "review": ["open", "resolved"]}'`.

1. **The scope.** Ask the owner, in one prose question, which part of the project the plan covers: the paths that hold the code and the tests the plan covers, as paths or globs, `.` for the whole project. From the answer, propose the paths, and record them beside the owner's words: `tasks item add --pool scope --key scope --field 'paths=["<path or glob>", ...]' --field said="<the owner's words>"`. A file lies inside the scope where it equals a path, lies under a path that is a folder, or matches a path that is a glob, where `*` crosses `/`. To change the recorded scope, run `tasks item set <the scope item> --field 'paths=[...]' --field said="<the owner's words>"`; the run holds one scope item, and `tests plan` refuses a run with none or with more than one.
2. **The programs.** Where the window's status is not `current`, file one programs task: `tasks file --role programs --prompt programs --agent ok-opus --key programs --brief "scope: <the owner's words> (paths: <the paths>); the last run is at <the results path, or none>"`. Drain with the drain loop at `.claude/skills/_tasks/drain.md`. List the questions it raised: `.ok-planner/bin/tests plan --sprint .ok-planner/test-sprints/<name>.md --from-run .ok-planner/test-sprints/<name>-planning.jsonl --questions`. Ask the owner each program question, one per turn, in prose: say what the program does. The owner picks one: *file an issue* that asks `/plan-sprint` for the story it serves, filed with `.ok-planner/bin/issues file --from -` per the `{{ISSUE-FILE-FORMAT}}` block of `skills/_shared/artifact-definitions.md`, kind `human`, category `product-intent`, the program and what it does as its `problem`; or *no guard*, with the reason, so later plans do not ask again. Record each answer with the `tasks item set` line step 7 gives.

## 6. Plan

Every planner's brief carries the scope, in the owner's words and as its paths, and each program answer: the program's path, its answer, and the reason for no guard. Below, `<the inputs>` stands for `scope: <the owner's words> (paths: <the paths>); program answers: <each path: issue <the issue id> | no-guard, <the reason>; or none>`, the `inputs` line `tests groups` prints, and `<the last run>` for its `last run` line, the results path or `none`.

1. **The groups.** Run `.ok-planner/bin/tests groups --sprint .ok-planner/test-sprints/<name>.md --from-run .ok-planner/test-sprints/<name>-planning.jsonl`, and on a widen run add `--widen` with the story slugs the owner named, or with none. It writes the groups beside the test sprint, `-groups.json` in place of `.md`, and prints each group's key, its stories with the reasons each is touched, and its brief. Where the window's status is `new`, every story is touched. Otherwise a story is touched where its file changed since the stamp, where a `@story:` annotation citing it sits in a file changed since the stamp, where its recorded test failed in the planning results, or, with the reason `slow <scenario> (<seconds>s)`, where its recorded test is among the `testing.slowest` slowest tests there, ranked by what each test adds to the run's wall time with the stamp's budget workers: a test that declares shared resources adds its whole seconds, and an isolated test its seconds divided by the workers; every other story's scenarios stand as recorded. A planner rewrites a slow test at a cheaper reach where its time comes from a named waste, and keeps it otherwise. The test sprint's own speed review reads the slowest tests of each passing round the same way. On a widen run, each story the owner named is touched with the reason `widen`, and with no slug, each story whose earlier calls, as `tests calls` lists them, left a path out. Where the verb prints `nothing to plan`, tell the owner that no earlier plan's call left a path out of a story, and stop. Stories one file cites join one group of up to 8, split in catalog order, and the other touched stories are batched by 8 in catalog order. It refuses a run with a program question the owner has not answered: ask it as step 5 says, and run the verb again.
2. **The planners.** File one story task per group, with the brief the verb printed for it: `tasks file --role story --prompt story --agent ok-opus --key group:<n> --brief "<the group's brief>"`. Where the verb prints `runtime planner: yes`, file one runtime task: `tasks file --role runtime --prompt runtime --agent ok-opus --key runtime --brief "<the inputs>; the last run is at <the last run>"`. Drain with the drain loop at `.claude/skills/_tasks/drain.md`.
3. **The sort.** Where the window lists test files no scenario claims, or claimed tests a person edited, file one sort task per ten of those files, in path order: `tasks file --role sort --prompt sort --agent ok-opus --key sort:<n> --brief "<the inputs>; files: <the paths>"`. Under any runner, mark each claimed test file the window lists as edited `claimed` in the brief, so a sort agent sorts each test in it that is no claiming scenario's own test. A sort agent records each test by its name, and a file that holds no test by its path. A sort agent records each fixture, helper, or data file with the tests that read it, whatever batch those tests fall in. Drain.
4. **The budget.** On every plan, after the sort, file one budget task: `tasks file --role budget --prompt budget --agent ok-opus --key budget --brief "<the inputs>; the last run is at <the last run>"`. It budgets the test stack the whole suite spends: the number of workers, the command that starts the test stack or `none`, the sizing its configuration gives for that many workers, the configuration files the preflight may edit, and, for each deployment-wide limit the tests meet, whether the configuration raises it, the workers split it, or a lease hands it out. Drain.

A task that closes `partial` is refiled whole with `tasks refile <task>`: the latest done task of each key stands, and its items replace the earlier task's. Each story's items come from the highest-numbered of those story tasks that records a `stories` item for it, so a one-story re-plan replaces that story's items alone.

**Fixing a planner's items.** One rule covers every fix to a planner's items: an assembly failure (step 8), a test the runner does not run (step 9), a review finding (step 11), and a change the owner asks for at approval (step 12). A fix is mechanical when the failure, the finding, or the owner's words name the whole change: a rename, a drop, a fold of named scenarios into one, or a wording fix whose new words they give. The session applies a mechanical fix itself, with the tracker's verbs, to the item the failure or finding names, and the items stay under the planner's task:

- **A rename** sets the item's id: `tasks item set <item> --field id=<new id>`. It then sets the new id on every question whose `scenario` field names the old id, and on every legacy item whose `scenario` field or `scenarios` list names it.
- **A drop** runs `tasks item drop <item> --by plan-tests --reason "<the failure or finding>"`, and drops each question whose `scenario` field names the dropped scenario the same way, so the dropped item leaves the plan.
- **A fold** drops every folded item but the one it keeps, as a drop does, sets the kept item's body to the folded outcome with `tasks item set <item> --body "<the outcome>"`, and sets the kept id on each legacy item that names a folded id, as a rename does.
- **A wording fix** sets the item's body: `tasks item set <item> --body "<the new words>"`.

A drop or a fold is mechanical only for a scenario the stamp did not record: a recorded scenario needs an action, `keep`, `retire`, or a question, and choosing one is the planner's judgment. Every other fix needs the planner's judgment, and goes back once every mechanical fix is applied. A judgment fix to a story's items re-plans that story alone, in a story task keyed `story:<slug>` whose brief is the story's group brief narrowed to that story: `tasks file --role story --prompt story --agent ok-opus --key story:<slug> --brief "stories: <slug> (<its reasons in the groups file>); <the inputs>; the last run is at <the last run>; revise task <the task its items came from>: <each failure or finding that names the story>"`, or, where a `story:<slug>` task already planned it, `tasks refile <that task>` with the same brief. A touched story no story task planned re-plans the same way, with no `revise` part. Every other judgment fix goes back as a revision refile of its planner: `tasks refile <its task> --brief "<its brief>; revise task <its task>: <each failure or finding that names it>"`. One re-plan per story, and one revision refile per other planner, carries every judgment fix that names it. Drain, and ask any question a revised planner raises, as step 7 does. Mark a finding `resolved` with `tasks item set <finding> --state resolved` once its fix is applied, by either path. After the fixes, assemble again, as step 8 does, and check the plan against the runner again, as step 9 does. The rule above for a task that closes `partial` stands: such a task is refiled whole.

## 7. The owner's answers

List the questions no answer settles yet: `.ok-planner/bin/tests plan --sprint .ok-planner/test-sprints/<name>.md --from-run .ok-planner/test-sprints/<name>-planning.jsonl --questions`. An answer stands for its scenario or program, so a refiled planner that raises the same question again is not asked twice. Each question is about a scenario whose outcome changed, or whose code is gone. Ask the owner each one, one per turn, in prose: name the scenario, the commit, and what it changed for the user. The owner picks one: *retire* the test; *rewrite* it to the new behavior, with the outcome the owner states; or *file an issue* so a sprint restores the old behavior, and the test stays failing until it does. For an issue, file it with `.ok-planner/bin/issues file --from -` per the `{{ISSUE-FILE-FORMAT}}` block of `skills/_shared/artifact-definitions.md`, kind `human`, category `product-intent`, the change as its `problem`.

Record each answer on its question: `tasks item set <question> --state answered --field answer=<retire | rewrite | issue | no-guard> --field said="<the owner's words>" [--field text="<the new outcome, for a rewrite>"] [--field issue=<the issue id>] [--field reason="<the reason, for no guard>"]`.

## 8. Assemble

Run `.ok-planner/bin/tests plan --sprint .ok-planner/test-sprints/<name>.md --from-run .ok-planner/test-sprints/<name>-planning.jsonl`. It reads the run's scope item and the groups, writes the plan beside the test sprint, `-plan.json` in place of `.md`, and prints the counts. It takes each story's scenarios, questions, and calls from the latest story task that records a `stories` item for it, keeps each recorded scenario of a story no group lists, each recorded runtime scenario where no runtime planner ran, and each recorded scenario of a story whose every reason is `widen` or `slow` that its planner names nowhere, and refuses each touched story no story task planned. It retires each scenario whose story is gone, adopts a legacy test in place of a new one where a sort agent adopted it, and keeps the first of two legacy tests adopted into one scenario, sorting the second as a duplicate. Where `testing.named` is `false`, an adopted scenario's test is the whole file, so the tests of one file adopted into one scenario stand together as its test. It refuses each claimed test file a person edited that no sort agent sorted. It keeps each fixture a kept test uses as that test's support, and deletes each one no kept test uses as an orphan. It refuses each deletion or port of a file a kept scenario names as support, and each support entry that names no test that reads it. It takes the budget and its limits from the latest done budget task, and refuses a run whose latest done budget task records no budget item or more than one, workers that is not a whole number of 1 or more, a budget that names no stack or no sizing, a limit handled other than by `raise`, `split`, or `lease`, and a scenario whose `resources` is not a list of slugs. It takes each time control from the `controls` items, one per id, and refuses two items that record one id with different fields, each `new` or `rewrite` whose `waits` names none of `event: <what the product emits>`, `control: <a time control>`, and `clock: <the clock the test moves>`, a `waits` that names a `control--<slug>` no item records, and each time control whose form is not `trigger`, `clock`, or `setting`, that names no site or no files, that names no gate setting where it is a trigger or a clock or one where it is a setting, or that no planned scenario waits on. It refuses each `new` or `rewrite` that names no kind or no setup, and each one a planner planned whose test path, support files, or entry lie outside the scope, or whose entry is a program the stamp or a no-guard answer leaves unguarded. Where it refuses, it names each failure and the item it rests on, as `<item id> (task <task id>)`: fix each one as "Fixing a planner's items" in step 6 says, and assemble again.

## 9. The runner check

After the last assembly, check that the suite command runs every planned test. `.ok-planner/bin/tests plan --sprint .ok-planner/test-sprints/<name>.md --show` lists, in its summary, each kind and setup pair of the planned `new` and `rewrite` tests with its count. Compare each pair with `testing.run` and `testing.silence`: the suite command runs a test of that kind, with that setup in place, and one test of the pair finishes, its setup included, inside the silence period, so its result line lands before the run stops. A suite command that runs files under a unit runner does not run a test that needs a browser, and a silence of 30 seconds does not hold a test whose stack takes a minute to start.

For each pair the suite command does not run inside the silence period, ask the owner, one question per turn, in prose: name the pair, its count, and what the command or the silence period lacks, and propose the change. The owner picks one: *change the command*, *change the silence period*, or *neither*. On a change, run `.ok-planner/bin/tests declare --run "<the command>"` or `.ok-planner/bin/tests declare --silence <seconds>`, and compare every pair again.

Where the owner changes neither, the planners of that pair's tests re-plan them in a form the suite command runs. `.ok-planner/bin/tests plan --sprint .ok-planner/test-sprints/<name>.md --show --json` names each scenario's kind, setup, and source. Each `new` and `rewrite` scenario carrying the pair is a judgment fix to its planner's items, applied as "Fixing a planner's items" in step 6 says: a story scenario re-plans its story alone, and a runtime scenario goes back as a revision refile, each finding naming the scenario and why the suite command does not run it inside the silence period. The planner plans the test in a form the suite command runs inside the silence period, and records a call of kind `untested` for each outcome no such form reaches. Drain, ask any question a revised planner raises, as step 7 does, assemble again, as step 8 does, and check again. The step ends when the suite command runs every pair inside the silence period, so the test sprint's unattended run meets no runner question.

## 10. Draft

Write the test sprint to `.ok-planner/test-sprints/<name>.md` from `{{TEST-SPRINT-DOCUMENT-TEMPLATE}}` in `test-sprint-document.md`: the window, the scope and the owner's answers, and the counts the last assembly printed. Copy the boilerplate verbatim.

## 11. Review

After the last assembly, file one review task per planner task the assembly reads, the latest done task of each key: each `group:<n>`, each `story:<slug>` re-plan, `runtime`, and each `sort:<n>`. `tasks report` lists each task's key, role, state, and outcome. A story task's review names only the stories whose items the assembly takes from that task, as step 6 picks them: each story whose `stories` item that task records and no higher-numbered done story task records, from `tasks item list --pool stories --json`. A story task whose every story a later re-plan took gets no review. Per planner task: `tasks file --role review --prompt review --agent ok-opus --key review:<its key> --brief "review task <its task id> (<its key>); stories: <the stories the assembly takes from it, or none>; <the inputs>"`. Then file one plan-wide review task: `tasks file --role plan-review --prompt plan-review --agent ok-opus --key review:plan --brief "review the plan; <the inputs>"`. The programs task and the budget task get no review of their own: the plan-wide review checks the owner's answers to the programs task's questions, and the shared resources the planned tests declare and the budget. A finding on the budget is a judgment fix, and goes back as a revision refile of the budget task. Drain with the drain loop at `.claude/skills/_tasks/drain.md`.

List the findings: `tasks item list --pool review --state open --json`. Each finding names its site, the planner task its `refile` field names, and the fix. Apply each one to that planner task's items, as "Fixing a planner's items" in step 6 says: a mechanical fix in place, and a judgment fix to a story's items by re-planning that story alone. A finding whose `refile` is `none` names a scenario no task of this run planned: a story's scenario re-plans its story the same way, and a runtime scenario goes to a runtime task filed as step 6 files one, its brief ending in the finding. Mark each finding `resolved` once its fix is applied, assemble again, as step 8 does, and write the new counts into the test sprint. The review runs once: a re-plan a finding sends gets no second review.

## 12. Approval

Present the test sprint for approval, with the output of `.ok-planner/bin/tests plan --sprint <its path> --show`. It opens with the scope, then leads with a summary: the count of scenarios per story by action, every call of kind `untested` or `departure` in full, the other calls grouped by kind, one line each, each kind and setup pair of planned tests with its count, each shared resource a planned test declares with its tests, the test stack's budget with each limit's handling, and each time control the plan builds, with its form, its site, its files, its gate setting, and the scenarios that wait on it. The test sprint builds each time control as product code before any test task runs, so the owner's approval of the plan approves each one. The whole listing follows: every scenario with its action, every legacy test with its sort, and every call a planner made. The owner approves the whole plan once, and it is not final until the owner approves. A change the owner asks for is a fix to the items of the planner it touches, applied as "Fixing a planner's items" in step 6 says; then write the new counts into the test sprint and present it again.

## 13. Terminal

Hand the owner the line that starts execution under the native `goal` mechanism, with this test sprint's filename stamped in, whole:

    /goal .ok-planner/test-sprints/<name>.md

The executing session states the goal's stop condition in its first message, as the test sprint's boilerplate says.

Then stop. The session writes only the test sprint, the files beside it that start with its name, the keys of `testing` (`run`, `silence`, `named`, `leftovers`, `slowest`, and `runners`) through `.ok-planner/bin/tests declare`, and the issues it files through `.ok-planner/bin/issues`.
