# Converge (find, then fix)

The run's estate is `.ok-planner/review/`: the catalogs under `catalog/`, the project's settings in `config.json`, the project's facts in `project.md`, and one ledger and folder per run under `runs/`.

**The run finds, then fixes.** It runs two loops, one after the other, and each one ends on its own terms:

1. **Find.** The mode decides how the run finds defects, and a merge agent folds every report into one defect list.
   - In `drive` mode the finders are drivers, one per story, each trying once to get what its story promises by using the product: on each surface it drives every variant the story's own text names, judges each on its own, and acts in the order a first-time user would. Where a story is offered through a skill, its driver reviews the skill text against the story instead. Drive mode drives every story, through the shared drive text that `/drive` runs alone, and fixes what the merge keeps.
   - In `analysis` mode hunters read the code: each area at least twice, file areas through two lenses of the accept list (`failure`: A3, A4, A5, A9; `state`: A1, A2, A6, A7, A8) and flow areas, one per file the surface intent names as declaring a class of public entry point, along the path of each entry point that file declares, save one the code exposes only behind a gate setting, an on-off setting that exists to expose debug or test elements, and at most a set number of times, and hunting stops per area when a hunt adds few new defects relative to what the area has shown. Each run hunts one slice of the areas and finishes it whole; the next run takes the next slice.
   - In `sprint` mode, sprint certification, the run certifies one executed sprint: one review of the sprint's change for completion and regression, the project's checks over the changed files, a drive of the sprint's new and changed stories where `testing.enabled` is `on` or `frozen` and of every story where it is `off`, and, where `testing.enabled` is `on` or `frozen`, a whole-suite round of the project's tests, each failing test rerun alone before a fixer is filed for it. The review's reading fixes the run's scope.
   - In `defects` mode the run finds nothing new: the defect backlog is its whole input.
   - `drive`, `analysis`, and `defects` mode take up the defect backlog: every `category: defect` issue in the intake that no sprint has promoted becomes a report.
2. **Fix and verify.** Fixers work through the defect list once. Verifiers read only the change each fixer made. A fix a verifier sends back is fixed again, until none is sent back or a defect reaches its limit of send-backs. A defect whose source is the suite has no limit and never goes stuck: it is fixed again until its test passes, or a verifier agrees that only a change to what the corpus commits to meets the test, and once no defect stands open, a final whole-suite round reopens the loop for each test it finds failing. A defect at its limit is stuck: a restorer returns the code its fixes changed to the behavior it had before them, keeping each change another defect needs, a verifier checks the restoration, and the defect goes to the intake as a judgment issue.

Neither loop re-hunts code a fix changed. New code a fix adds is checked by its verifier against the accept list and the release boundaries, and the next run's hunt reads it as ordinary code. That is what keeps the run finite: the old loops re-read every file a fix touched, and every re-read found something new in the code the last fix had added.

**The accept list decides what is a defect.** `.ok-planner/review/catalog/accept.md` names the harms the run fixes: stored state left half-changed, a write on the wrong target, an end user able to break the product, a unit of work ending with no record, ongoing work that stops or wears down, access granted or kept wrongly, accepted data lost, skipped, or doubled, code that breaks a rule the project states where the rule decides the fix, and a report that tells someone something false. Every finder, merge agent, fixer, and verifier reads it. A site the list does not cover stands. `.claude/rules/plumbline-coding.md` governs catches: a library's error that reaches the owner frame is not a defect. In `sprint` mode the sprint's own promises count too, under the sprint catalog `{{SPRINT-CATALOG}}` in `.claude/skills/_sprint/shared.md`.

**Release boundaries bind every fix.** `.ok-planner/release-boundaries.md` names the users that do not update when the code does. Stored state is always one, and so is the public surface: every element the surface intent at `.ok-planner/surface/surface.md` classes as public. A fix keeps them working unless a ruling of the sprint in scope allows otherwise.

**The intent is to fix, not to file.** Every defect on the list is fixed in the run, declined with a reason a verifier accepts, stuck, or, for a defect the suite found, `promised`: a verifier agreed that only a change to what the corpus commits to meets its test. A stuck defect's fix failed twice, so what fixes it is a judgment: the code its fixes changed is restored and it becomes a judgment issue. What the run meets outside its scope goes to the intake, per the Defect issues section of `.claude/rules/ok-planner-cheatsheet.md`: a defect the accept list decides becomes a `category: defect` issue, for the next `drive`, `analysis`, or `defects` run; anything that needs the owner's judgment, about the product or about the project's own tooling, becomes an issue in any other category, for the next `/plan-sprint`. A harm whose fix lies in a part the project does not own — a file the suite owns, such as this skill, its prompts, or the catalogs; a library the project depends on; an outside tool or service; or the accept list itself, for a harm it does not name — becomes an upstream issue in the intake, `category: upstream`, with a draft ready to file, for the next `/plan-sprint`. The run asks the owner nothing about it.

**The run never waits on the owner while it finds and fixes.** It ends with every fix it kept verified, the code of every fix it could not verify restored, or, where a restoration could not settle, the state it left named in the intake, and everything else in the intake. The owner reads the report, vetoes any call the run's agents made without the owner, and decides whether to archive and commit.

Every mechanical step is a verb of `.ok-planner/bin/review`, in sprint certification also of `.ok-planner/bin/tests`, or an `exec` task. Every agent is a task in the task tracker at `.ok-planner/bin/tasks`, drained by the drain loop at `.claude/skills/_tasks/drain.md` under a vendored profile, or a fork of the sprint review root. The skill dispatches no agent directly. The session reads no file for judgment and edits no file but the run's ledger, save the intake at the close of a `drive`, `analysis`, or `defects` run, where it files one issue per call the owner vetoes, through `.ok-planner/bin/issues` alone.

## Scope

**Every file the project owns, by ownership, not location.** A run fixes a clear defect in every file the project owns, wherever it sits, under `.claude/` and `.ok-planner/` too: its code and tooling, its configuration, its review facts, and its release boundaries. Its documentation is a documentation sprint's to write and check, so no run of `/converge` reviews it. It leaves four kinds of file alone: the design corpus, the coding standards, the docspecs and their index, and the surface intent, which change only through a sprint's deltas, save that sprint certification lands an approved delta of the sprint it certifies that execution missed, as a C3 defect, the one corpus write a review run makes; a file the suite owns, whose harm goes to the intake as an upstream issue; the harness settings (`.claude/settings.json`, its siblings, and `.mcp.json`), whose defect goes to the intake as a judgment issue; and a record, which changes only through the act that owns it and about which the run files nothing. `review owner <path>...` prints each path's kind: `project`, `suite`, `corpus`, `declaration`, or `record`. `{{FIX-LINE-RULE}}` in `.claude/skills/_converge/coding-rules.md` states the rule every merge, fix, verify, restore, sprint review, and sprint pass prompt carries.

**Code, and skill text.** The analysis hunt reads code alone: `review files` lists its population: every tracked or untracked file under the project root and under each folder `.ok-planner/config.json` declares under `folders` that is not prose (`.md`, `.markdown`, `.rst`, `.txt`), not binary, not at a test path, not a file `review owner` classes as anything but `project`, and not under an excluded path in `.ok-planner/review/config.json` (the paths the project adds).

In `sprint` mode the sprint's alignment pass reads the design corpus under `.ok-planner/design/` to compare it with the sprint's deltas. Skill text is code: a prompt an agent session runs in the project, whether the product ships it or the project keeps it for its own work, such as a skill, a rule, or an agent profile. A driver reviews a story's skill surface, the sprint review reads skill text the sprint's change reaches, a defect issue may name it, and fixers fix it as code. Other prose is in review only where the sprint the run certifies added or changed it, and never where it is documentation: a file under a docspec's `## Where`, or a doc comment in a file an in-code docspec covers. `{{PROSE-SCOPE-RULE}}` in `.claude/skills/_converge/coding-rules.md` states the rule every merge, fix, verify, sprint review, and sprint pass prompt carries.

**The invocation** takes optional arguments, in any order:

- `drive`, `analysis`, `defects`, or `sprint <path>`: the mode, and for `sprint` the sprint's path under `.ok-planner/sprints/`.
- `--only <path or glob> ...`: in `analysis` mode, hunt only the file areas holding a matching file and the flow areas whose declaring file matches. It limits the hunt alone: a fix reaches every file it needs.

**Ask for the mode.** Where the invocation names no mode, ask the owner before anything else, in one plain-text line, not a form: `Drive (the default) or analysis?` Wait for the answer. An answer that names neither, or accepts the default, means `drive`. `defects` and `sprint` mode are named, never defaulted to.

**Where it runs.** On the branch the working tree has checked out. A working tree with a merge in progress (`git rev-parse --verify --quiet MERGE_HEAD` resolves) is refused. Uncommitted work that stands before the run is left as it stands: agents stage by name and never discard.

## Setting up the run

1. **Preconditions.** `.ok-planner/bin/tasks`, the profiles under `.claude/agents/`, and `.ok-planner/review/` with its `config.json`, `project.md`, and `catalog/accept.md` exist; otherwise say which is missing and stop. Run `.ok-planner/bin/issues list`. Where it refuses because the intake holds an earlier layout, say that `/ok` converts it, and stop. It writes a note on stderr for each stray line it skips; say each note in the return, and go on. In `sprint` mode, first run `.ok-planner/bin/review approved --sprint <the sprint's path>`, before the base file is read or written. Where it refuses, say its message and stop, with no return block: the sprint may be a draft the owner never approved, and writing its base file would exempt it. Then read the sprint's base file (beside the sprint, `-base.txt` in place of `.md`); where it is missing, ask the owner once for the base commit and write the file from the answer. The sprint's build run file (`-run.jsonl` in place of `.md`) is read where it exists; a sprint built without one has no build divergences or noticed defects, and says so in the return. Then run `.ok-planner/bin/tests enabled`: the word it prints, `on`, `frozen`, or `off`, is the run's testing state, and decides whether the run takes the suite. Where `.ok-planner/bin/tests` is missing or the verb refuses, say so with its message, and stop, with no return block. Say the run's shape in one line before it starts: the mode; for `defects` the count of `category: defect` issues it takes up; for `analysis` the count of file areas and flow areas, the hunt settings (`min`, `max`, `threshold` from `config.json` `hunt`), and any `--only` limit; for `sprint` the sprint, its base commit, the count of changed files, the count of stories the drive takes, counted from `review stories --sprint <the sprint's path>` where the testing state is `on` or `frozen` and from `review stories` where it is `off`, the paths outside the project root it lists, whether a build run file exists, and the testing state. Where any `review` or `tests` verb refuses because `.ok-planner/config.json` sets a malformed `folders`, or because node is not on PATH to check the folders it declares beyond the project root, say its message and stop, with no return block. The changed files are what `review changed --base <base>` lists: every file added, changed, or deleted since the base under the project root and its declared folders, untracked files included, relative to the project root, less the files `review owner` classes as anything but `project` (so a changed harness settings file, corpus file, or record is not on the list) and the paths `.ok-planner/review/config.json` lists under `exclude` and `test_patterns`. In `sprint` mode every `review changed`, `review checks`, and `review snapshot` call adds `--sprint <the sprint's path>`, so the list also holds the files changed under each folder the sprint lists under `## Paths outside the project root`, as paths relative to the project root, such as `../runtime/build`. `review checks` runs each check over the added and changed ones.
2. **Open a fresh ledger.** `tasks init converge-<date>T<time> --file .ok-planner/review/runs/converge-<date>T<time>.jsonl`, the timestamp from `date +%Y-%m-%dT%H%M%S`. Never `tasks use` an existing file to open the run. The run's folder is `.ok-planner/review/runs/converge-<date>T<time>/`.
3. **Register the profiles**: `tasks agent register ok-opus`; in `drive` and `sprint` mode `tasks agent register ok-drive`, the profile `review drives` files every driver and confirm driver under; in `sprint` mode `tasks agent register ok-review`; and in `sprint` mode, where the testing state is not `off`, `tasks agent register ok-test`, the profile `.ok-planner/bin/tests tasks` files the test support, test, verify, and speed tasks under.
4. **Assemble and register the prompts**, each written into the run's folder by `review prompt --name <name> --out <folder>/<name>.md` and registered with `tasks prompt register <name> <path>`: `merge`, `fix`, `verify`, `restore`, and `owner-list` always; `drive` and `drive-start` in `drive` and `sprint` mode; `hunt-file` and `hunt-flow` in `analysis` mode; `sprint-review` and `sprint-pass` in `sprint` mode. In `sprint` mode, where the testing state is not `off`, also the test stages' prompts, each registered under the role name `.ok-planner/bin/tests tasks` files its tasks with: `test-write` as `test`, `test-support` as `test-support`, and `test-speed` as `speed`, and `test-verify` as `test-verify`, since `verify` names this run's fix verifier. In `sprint` mode every `review prompt` call adds `--sprint <the sprint's path> --base <the base commit>`, so every prompt names the sprint whose rulings bind the fixes.
5. **Declare the vocabulary**: `tasks config set item_states '{"reports": ["open", "merged", "rejected", "backlog", "judgment", "upstream"], "defects": ["open", "fixing", "fixed", "declined", "duplicate", "verified", "stuck", "promise", "promised", "at-fault", "rewrite"], "failures": ["open", "defect", "not-owed", "environment", "redrive", "backlog", "judgment", "upstream", "rejected"], "merges": ["done"], "calls": ["open", "promoted"], "tests": ["open", "accepted", "sent-back"], "test-support": ["open", "made"], "promises": ["open", "held", "rejected"], "speed": ["accepted", "sent-back", "product-slow"]}'`, and the fields the tests tool reads as numbers: `tasks config set field_types '{"tests": {"silence": "integer"}, "speed": {"seconds": "number", "rank": "integer"}}'`. A suite defect's fixer records `promise` where only a change to what the corpus commits to meets its test, and `at-fault` where the test, its test support, its fixture, or its data is at fault; its verifier sets `promised` where it agrees with a promise, and `rewrite` where it accepts a fault and sends each test it names back to a test task through the `tests` pool. A T4 defect, a schedule breach, takes no fixer: the merge files it at `rewrite`, and a test support task fixes it. `tasks config set swept_roles '["fix"]'`, and `tasks config set calls '[{"pool":"defects","states":["declined","duplicate"]},{"pool":"failures","states":["not-owed","rejected"]},{"pool":"reports","states":["rejected"]},{"pool":"calls","kinds":["unlisted","untested","departure","scope","mechanics"]},{"pool":"divergences"}]'`, so `tasks calls` prints one row per judgment an agent of the run made without the owner, the calls step 5a's test stages record among them. Every task the session or a `review` verb files carries key `gate`; the test stages' tasks `.ok-planner/bin/tests tasks` files carry the keys that tool gives them.

## Loop 1: find and merge

**The merge rule**, which every merge of every mode obeys: a `merge` task that closes with any outcome but `done` is refiled once with `tasks refile <task>` and drained. After a second such close, name the merge in the return. In `analysis` mode, also record a count for each area and hunt its brief names that has none in the `merges` pool (`tasks item list --pool merges --key gate --json`): `tasks item add --pool merges --key gate --state done --field area=<area> --field hunt=<hunt number> --field new=0 --field matched=0 --field rejected=0 --field unmerged=<the count of the area's reports still open> --body "merge <task> closed <outcome> twice"`, so the tally stops that area instead of hunting it again. Every report and failure the brief names that still stands `open` goes to the owner list, which files it as a defect no merge agent judged.

### The backlog, in drive, analysis, and defects mode

Before the hunt, take up the intake's defect issues: every record in the live store, `.ok-planner/issues.jsonl`, with `category: defect` whose state is `open` or `verified` and whose `sprint` is not set, read through `.ok-planner/bin/issues`. A record whose `sprint` is set is promoted into that sprint and waits for its archive step, so the backlog leaves it alone. `review backlog` adds one report per issue: its `problem` as the body, its id in the `issue` field, every file its problem names that the run may edit, and, as the site, the first `path:function` its problem names whose path is among its files, else its first file. It works out every issue's report before it adds any. It adds every report in one write, or none. An issue whose problem names no file the run may edit adds no report: the verb lists it under `settled`, with `files: []` and each file it names that the run leaves alone, with its kind, under `left_alone`. For each settled issue, add its report yourself, so the merge agent routes it:

- Where `left_alone` names files, the ownership test routes it: `tasks item add --pool reports --key gate --field area=backlog --field hunt=1 --field issue=<the issue id> --field site=<its first left-alone file> --field 'files=[<its left-alone files>]' --body "issue <the issue id>: its problem names only files the run leaves alone: <each file and its kind>"`.
- Where `left_alone` is empty, the problem names no file of this tree outside the exclude list, and the report names no site: the merge agent finds the site the problem describes, or finds the defect gone: `tasks item add --pool reports --key gate --field area=backlog --field hunt=1 --field issue=<the issue id> --field 'files=[]' --body "issue <the issue id>: its problem names no file of this tree outside the exclude list"`.

A store that does not exist yet is an empty backlog. Where the backlog holds any report, `review merges --source backlog` files one `merge` task per `hunt.merge_reports` of them; drain, under the merge rule. The merge agent checks each against the code and merges the real ones, each carrying its issue's id.

In `defects` mode this is the whole of Loop 1. Where the intake holds no such issue, say so and end the run.

### In drive mode

Run the shared drive text at `.claude/skills/_converge/drive.md`, steps 1 to 6, over every story: `review stories` and `review drives`, with no `--sprint`. Drive mode takes every story every run: it is where the run spends its tokens. Once its step 6 merge is drained, or where the drive ends early, as a step of the shared text says, go to Loop 2 with what the list holds.

### In analysis mode

1. **The slice.** `review areas --out <folder>/areas.json`. It groups the code files by directory into file areas of about `hunt.area_lines` lines, one area for each lens in `hunt.lenses`, and cuts one flow area for each class of entry point and each file the surface intent at `.ok-planner/surface/surface.md` names under `## Where each class is declared` as declaring that class, named `flow:<class>@<path>`. Nothing stores the entry points: the flow hunter finds them in the declaring file, and leaves out each one the code exposes only behind a gate setting, an on-off setting that exists to expose debug or test elements, which stays internal and which the file areas hunt. Then it takes this run's slice: `hunt.slice` areas, file and flow areas in turn, those never hunted first, then those whose files changed since their last hunt, then those hunted longest ago, by the stamps in `hunt.rotation`. The run finishes its slice whole; the next run takes the next slice. Where the project has no surface intent, or the intent names no declaring file, the verb says so on stderr and the run hunts file areas alone; say so in the return. `--only` replaces the slice with the areas it matches.
2. **The first hunt round.** `tasks round start`. `review hunts --areas <folder>/areas.json --first --out <folder>/round-1.json` files hunts 1 and 2 of every area: a `hunt-file` task for a file area, whose brief names its lens and files, and a `hunt-flow` task for a flow area, whose brief names its class and its declaring file. Drain under a concurrency cap of **8**. A hunt task that closed `partial` is refiled once with `tasks refile <task>`; a second `partial`, or a close at `blocked` or `disputed`, is named in the return, and its area's count for that hunt stands at what its reports show.
3. **The merge.** `review merges --round <folder>/round-<n>.json` reads the round's open reports, groups the areas whose reports touch the same files into one merge task of at most `hunt.merge_reports` reports, and files it. It writes a zero count for each area and hunt that reported nothing, so those need no agent. Drain under a cap of **8**, under the merge rule.
4. **The tally.** `review tally`. For each area it prints the hunts run, the defects found, how many the latest hunt added that no earlier one had, a capture-recapture estimate of the defects no hunt has found yet (from hunts 1 and 2), and a decision: `hunt` while the area has had fewer than `hunt.min` hunts, `stop: converged` once the latest hunt added no more new defects than `hunt.threshold` allows (its `share` of the area's defects, or its `floor`, whichever is larger), `stop: cap` at `hunt.max` hunts. Say in one line how many areas hunt again and how many stopped.
5. **Later rounds.** `tasks round start`, then `review hunts --areas <folder>/areas.json --out <folder>/round-<n>.json`, which files the next hunt of each area the tally says to hunt, then the merge and the tally again, until no area hunts.
6. **Stamp the slice.** `review rotate --areas <folder>/areas.json` records each file area's files and each flow area's declaring file as hunted now, at this commit, with each file's content as the hunt read it. A file a fix later changes reads as changed, so a later run hunts it again early.

Hunters never see each other's reports, and never see the defect list. Their independence is what makes the tally mean something.

### In sprint mode

`/converge sprint <path>` is **sprint certification**: the run certifies one executed sprint, and the sprint's execution boilerplate names it as the closing step. Its change runs from the commit in the sprint's `-base.txt` file to the working tree. The standard is the sprint itself: its work items, its taken improvements, its deltas, and its implementation notes' rulings, beside the accept list. The review reads once, and its reading is the run's scope: nothing found later joins the list.

1. **The review.** `tasks round start`. File the review root: `tasks file --role review --prompt sprint-review --agent ok-review --key gate --brief "review"`. Drain. The root reads the sprint, the change, and the users the change reaches; files one `sprint-pass` task per pass (completion, regression, and alignment), forked from its own task; closes its task; and forks one agent per pass task in one message. Where the root's task closes with any outcome but `done`, or the run holds no pass task forked from it (`tasks dump --type task` shows each task's `fork_of`), refile the root once with `tasks refile <task>` (`tasks retry` refuses a `done` close) and drain. Where the second root also does not finish, the run stops: say that the review did not run, with each root's outcome and result, and present no return block, so the completion report carries no certification and the completion contract stays open. A pass task forked from a root that did not finish is left as it closes; the merge folds its reports with the others. A pass task the drain lists under `waiting` with `fork-of` after the root's agent returned is an orphan: `tasks retry <task>` and drain again. A pass task that closes with any outcome but `done` is retried once; a second such close is named in the return.
2. **The build's noticed defects.** Where the sprint has a build run file, `review noticed --build-run <the run file>` adds one report per `noticed` item in it, under the area `sprint-noticed`.
3. **The checks.** `review checks --base <the base commit> --sprint <the sprint's path>` files one `exec` task per check in `.ok-planner/review/config.json` `checks`, each run over the files added or changed since the base and nothing else, and prints the tasks it filed. Where no file was added or changed, it files none. Drain. For each failing file, file a report: `tasks item add --pool reports --key gate --field area=sprint-checks --field hunt=1 --field entry=M1 --field site=<the file> --field 'files=["<the file>"]' --body "<the check; the output>"`.
3a. **The suite.** Where the testing state is `off`, skip this step, and say in the return that the suite was skipped under `off`. Otherwise the suite is a find source. The four steps below run one whole-suite round and what follows it, and Loop 2's final whole-suite round, its step 2a, runs them again.
   1. **The round.** File one `exec` task, `tasks file --kind exec --key gate --command ".ok-planner/bin/tests run --sprint <the sprint's path>"`, and drain it. It records a whole-suite round in the sprint's `-results.jsonl`; a failing test does not fail the task. Where the task fails, name it in the return with its output tail, and go on with what the round recorded.
   2. **The speed read.** Where `.ok-planner/bin/tests failures --sprint <the sprint's path> --json` lists a failure, the round failed. Where it failed and the testing state is `on`, run the speed step before the next round runs: `.ok-planner/bin/tests tasks --sprint <the sprint's path> --stage speed --run <this run's ledger> --round <the round's number, the `round` that output prints>` files one speed task for each of the `testing.slowest` slowest tests of the round that has no speed acceptance at its current test file; drain, then run step 5a's test stages, so each speed rewrite lands in the round that must run anyway. Under `frozen`, or where the round passed, the run does no speed work here. Where every failure it lists but its `perf:` entries is a `schedule--` entry or a test whose `tail` opens `setup failed`, the round failed on a fault of the suite command or its setup, which no speed rewrite fixes: run no speed step for it.
   3. **Each failing test alone.** Run `.ok-planner/bin/tests failures --sprint <the sprint's path> --json`. For each failure it lists whose `scenario` is a test, not a `leftovers--`, `stopped--`, `schedule--`, or `perf:` entry, file one `exec` task, `tasks file --kind exec --key gate --command ".ok-planner/bin/tests run --sprint <the sprint's path> --only <the scenario>"`, and drain them under a cap of **8**. Each records a rerun round, so the report for its test says whether the test failed again alone or passed.
   4. **The reports.** `.ok-planner/bin/tests reports --sprint <the sprint's path>` adds one report under the area `sprint-suite` per failure of the round (T1), per stop of the round that left a test with no result (T1, a `stopped--silence` entry), per leftover count that grew in it (T2), per `perf:` entry beside another failure of the round, so the fix rides a whole-suite round that runs anyway (T3), and per `schedule--` entry (T4), and prints them, the failures already reported, and the failures a hold settles. Say the counts in the return.

4. **The drive.** The testing state picks the story set. Where it is `on` or `frozen`, the drive takes the sprint's new and changed stories: run the shared drive text at `.claude/skills/_converge/drive.md`, steps 1 to 5, with `review stories --sprint <the sprint's path>` and `review drives --sprint <the sprint's path>`. Where its step 1 prints no slug, skip the drive and say in the return that the sprint names no new or changed story: the completion contract then stands as it is. Where the testing state is `off`, the drive takes every story: run those steps with `review stories` and `review drives`, with no `--sprint`. Where `review stories` prints no slug, skip the drive and say so in the return: a project with no story leaves the completion contract as it stands. Where `review drive-stack` prints `unfilled` or refuses, or the drive ends without driving after its starts, as the shared text's step 2 says, the drive did not run: say so in the return with the reason, name every story the drive did not drive, and go to the merge. The completion contract then stays open, and `review certified` prints `SPRINT NOT COMPLETE` naming the drive that did not run, until a certification whose drive runs.
5. **The merge.** `review merges --source sprint` files the merges of the open reports, the suite's among them, and the shared drive text's step 6, `review merges --source drive`, those of the open failures, so the drive's failures merge once and fold with the other findings. Drain under a cap of **8**, under the merge rule. The merge agent merges each in-scope defect, and sets each real defect outside the sprint's scope to `backlog` for the owner list. Before the scope test, it applies the ownership test of merge step 3a to the file each fix lies in, as in every mode, even where the sprint's change edited the file or a delta names the artifact. A C3 report, a delta of the sprint that did not land, merges as a defect, and the fix loop lands the delta. Any other fix in the corpus, a docspec or the surface intent included, or a fix in the harness settings, sets the item to `judgment`, a fix in a file the suite owns to `upstream`, and a fix that lies only in a record to `rejected`. No agent of the run edits such a file, so it gets no fix round: the owner list files a `judgment` or `upstream` item in the intake, and files nothing for a record.

## Loop 2: fix and verify

Repeat, with `r` the fix round's number:

1. **Retire what cannot be fixed.** Every defect at state `open` whose `source` is not `suite` and whose `kickbacks` field has reached `config.json` `fix.max_kickbacks` is set to `stuck`, with the last verifier's note kept. A defect whose `source` is `suite` never goes stuck, whatever its `kickbacks`. The code a stuck defect's fixes changed is then restored with care, in a loop of its own:
   1. **Restore.** `review restores --folder <folder>` files one `restore` task per stuck defect with no `restored` field, whose `restore_kickbacks` field is still under `fix.max_kickbacks`, and whose last restore task a verifier has sent back or that has none. Its brief names every fix task that staged a change for the defect, every earlier restore task, and, for every file those tasks staged, its blob from the snapshot of the round that first fixed it. A stuck defect no fix task changed gets none. Drain under a cap of **8**. The restorer returns the code to the behavior it had before the defect's fixes, by judgment, keeping each change another defect needs. A restore task that closes with any outcome but `done` is refiled once with `tasks refile <task>` and drained.
   2. **Verify.** `review restores --folder <folder> --verify` files one `verify` task per closed restore task, read with its refiles as one chain, that no verifier has checked yet. Drain under a cap of **8**. The verifier checks that the prior behavior is back, that every other accepted fix still works, and that the project's checks pass on the changed files. It accepts the restoration by setting the defect's `restored` field to the restore task, or sends it back by raising `restore_kickbacks` by one; a send-back that brings `restore_kickbacks` to `fix.max_kickbacks` also sets `restored=stuck`, with the state the code was left in in its note. Where a verifier closed and left the defect's `restored` field unset and its `restore_kickbacks` at the count its brief names, send the restoration back yourself: raise `restore_kickbacks` by one, and where that brings it to `fix.max_kickbacks`, set `restored=stuck`, keeping the last verifier's note.
   3. **Repeat** from 1 until `review restores` and `review restores --verify` both file no task. Each send-back raises a count that has a ceiling, so this loop ends. The owner list files each stuck defect as a judgment issue, naming the restoration's outcome.
2. **End check.** Where no defect stands at `open` or `fixing`, every stuck defect a fix task changed has a `restored` field, and, in sprint mode, no defect stands at `rewrite` save one step 5a's write stage refused to serve, the loop ends, save in two cases. In drive and sprint mode, where `review drives --confirm --dry-run` lists any defect and the final confirm has not run in this run, run the final confirm once: `tasks round start`, then steps 6 and 6a, then go to step 1. The round of its own keeps its drive names and instance folders apart from those of the round before. In sprint mode, where the testing state is not `off`, the final whole-suite round, step 2a, runs before the loop ends.
2a. **The final whole-suite round, in sprint mode where the testing state is not `off`.** `tasks round start`, then run step 3a's round, its step 1. Then run `.ok-planner/bin/tests settled --sprint <the sprint's path> --ledger <this run's ledger>`. Where it prints `SETTLED`, the loop ends: a whole-suite round ran after the last change, and every test it found failing is held, by a `promised` defect or an owner issue. A product-slow verdict that round left standing as its only failure counts as deferred, not as a failure: `SETTLED` lists each deferred verdict, `tests failures --json` lists them under `deferred`, no product-slow fix lands after the round, and the owner list files each one for the next `/plan-sprint`. Where it prints `NOT SETTLED`, it names each failure:
   - Where `.ok-planner/bin/tests failures --sprint <the sprint's path> --json` lists a failure, the round failed. Then run step 3a's steps 2 to 4, the speed read, each failing test alone, and the reports, then `review merges --source sprint`, drained under the merge rule, and go to step 1. The review passes, the checks, and the drive do not run again: only the suite reopens the loop.
   - Where it names a speed send-back that no accepted rewrite settles and whose test file does not stand at the blob it names, and step 5a's stages file nothing for it, the rewrite did not settle. Send the test back to its last passing version: `tasks item add --pool tests --key <the scenario> --field scenario=<the scenario> --state sent-back --field reason="return the test file to blob <the blob>, its last passing version: its speed rewrite did not settle, and the speed send-back stays open for the next sprint" --body "<the same reason>"`, run step 5a, and run this step again.
   - Otherwise a task changed a file outside the test paths after the round, or a test ran in no round since it: run this step again.

   A speed rewrite that fails a whole-suite round is a failing test like any other: its fixer finds the rewrite at fault, and the test task that rewrites it returns the test to its last passing version, so speed work never costs the sprint a whole-suite round of its own.
3. **Snapshot.** `tasks round start`, then `review snapshot --out <folder>/fix-<r>.json`. It saves the blob of every open defect's files and every file `review changed` lists as added or changed since `HEAD`, or every file before the first commit, stamped with the round. A fixer may widen into a file the snapshot leaves out; that file was unchanged when the round started, so the verbs below take its blob from `HEAD`.
4. **Fix.** `review fixes --round <r>`. It groups the open defects whose files overlap, or that a merge marked `same_as` one another, into one task, up to `fix.group_size` defects a task, chains the tasks of one overlapping group behind each other, and files every group apart from the others so they run together. Drain under a cap of **8**. A fix task that closed `partial` with a result starting `outside files:` waits for the task that held them: its fixer already widened those defects' files, so set its unfinished defects (those still `fixing`) back to `open` with `waits` raised by one and `kickbacks` unchanged, and they return next round grouped with the files they reach. A wait is not a send-back. A missing `waits` field counts as 0. Where a defect's `waits` already stands at `fix.max_kickbacks`, the wait raises its `kickbacks` by one instead. A fix task that closes `blocked` or `disputed`, or `partial` with any other result, is refiled once with `tasks refile <task>` and drained. Once a fix task and its refiles have closed, after the wait above, every defect of the round it still leaves at `fixing` goes back to `open` with `kickbacks` raised by one, whatever the close: a second failed close, or a `done` close that left the defect at `fixing`. So a defect no fixer can finish reaches `stuck`, and the owner list files it as a judgment issue. Every fix task of the round closes before any verifier starts.
5. **Verify.** `review verifies --snapshot <folder>/fix-<r>.json` files one `verify` task for every fix task of the round, read with its refiles as one chain, that set any defect `fixed`, `declined`, `duplicate`, `promise`, or `at-fault`, naming those defects and, for every file the chain staged, its blob from the snapshot or from `HEAD`. It also lists under `fixing` each defect a closed chain left at `fixing`. Before draining the verifiers, send each defect it lists there back to `open` with `kickbacks` raised by one, as step 4 does. Drain under a cap of **8**. A verifier that accepts a decline or a duplicate leaves its state and sets its `verified` field. A verifier sets a suite defect's `promise` to `promised` where it agrees, and its `at-fault`, or a `promise` it rejects because the test is at fault, to `rewrite`, sending each test the fault names back through the `tests` pool. A defect still `fixed`, `promise`, or `at-fault` after its verifier closed, or still `declined` or `duplicate` with no `verified` field, goes back to `open` with `kickbacks` raised by one.
5a. **The test stages, in sprint mode where the testing state is not `off`.** A test changes only through a test task. For each defect at `rewrite` whose `entry` is T4, a schedule breach, and whose `test_support` field is missing or `none`, add one `test-support` item for the file its `files` field names first, the suite command's file that runs the schedule: `tasks item add --pool test-support --key <that file> --field path=<that file> --field scenario=<the first test its test field names> --field change=changed --body "<the defect's body>"`, then `tasks item set <the defect> --field test_support=<the item>`. Then run `.ok-planner/bin/tests tasks --sprint <the sprint's path> --stage write --run <this run's ledger>` and drain, then `.ok-planner/bin/tests tasks --sprint <the sprint's path> --stage verify --run <this run's ledger>` and drain, and repeat both until neither files a task. The write stage files a test support task for each open `test-support` item and one test task per story, or per chunk of at most `testing.chunk` of the story's tests, for the tests a verifier or a speed reviewer sent back, each with the reason, and every test task it files waits on every test support task it files in that pass; its refusals and refiles count per test task, not per scenario. The verify stage files one `test-verify` verifier per test task, for every record that task made. Where the write stage refuses, it files nothing: say its refusal in the return. The `rewrite` defects it would have served stand as they are, and the end check does not wait on them.
6. **Confirm, in drive and sprint mode.** `review drives --confirm --dry-run` prints `{"pending": [{"defect", "story", "surface", "folded"}]}`, one entry per confirm driver it would file, and files nothing. It takes every verified defect that no confirm driver has marked `confirmed`, from any round, whose `source` is `drive` or that a verifier folded a drive defect into: a defect at state `duplicate` whose `source` is `drive`, with a `verified` field and `same_as` naming it. A defect whose `source` is `drive` gets one entry for its own stories, with no `surface` or `folded`. It also gets one entry, with `surface` and `folded`, per story and surface its folded duplicates name that its own entry does not cover. Where it lists any defect, start the stack unless `review drive-stack` prints `none`: file one `exec` task whose `--command` is what `review drive-command --role stack-start` prints, in the form step 2 of the shared drive text gives, and drain it. Where the start fails, run the `drive-start` tasks of step 2 of the shared drive text, within its 3 starts. Where the drive ends without driving, say so in the return with the cause the last `drive-start` result names, name the defects left unconfirmed, file no confirm driver and no `stack-stop` task, and go to step 6a. Where the stack started, or the project has none, run `review drives --confirm`, which files one confirm driver per entry the dry run listed, each defect's drivers chained one after another as a relay, and chained as step 3 of the shared drive text chains, with a drive name and with an instance folder where step 3 of the shared drive text names one, and drain them under a cap of **8**. Then stop what the round started as step 4 of the shared drive text does, in its order, over the `instance` folders and `name`s `review drives --confirm` listed: each `instance-destroy` and `resource-stop` first, and the `stack-stop` last where this step started the stack. A driver that gets the story marks the defect its brief names, the verified one: the last driver of the relay sets its `confirmed` field to its task, and each driver before it sets `confirm_reached`, so the next one drives. A driver sends its defect back when the story still cannot be got. It records no new failure: anything else it meets is the next run's.
6a. **Confirm each suite defect, in sprint mode where the testing state is not `off`.** List the defects whose `source` is `suite` that stand `verified` with no `confirmed` field, and those that stand `rewrite` with every test sent back accepted: the latest `tests` item of each, in this run's ledger, stands `accepted`, and for a T4 defect, its `test-support` item stands `made`. For each, file one `exec` task, `tasks file --kind exec --key gate --command ".ok-planner/bin/tests run --sprint <the sprint's path> --only <its tests>"`, its tests being its `test` field; for a `leftovers--<kind>` or `stopped--silence` defect, each test its `tests` field names; for a `perf:<scenario>:<speed item>` defect, its scenario; and for a `schedule--<a>--<b>` defect, `a` and `b`. Drain under a cap of **8**. Then run `.ok-planner/bin/tests failures --sprint <the sprint's path> --json`. A defect whose `test` it still lists, or, for a `perf:` defect, whose scenario it lists, goes back to `open` with `kickbacks` raised by one, save a T4 defect, which goes back to `rewrite` with `--field test_support=none`, so step 5a adds a fresh `test-support` item. Every other defect listed above gets `tasks item set <id> --state verified --field confirmed=<its exec task>`.
7. Go to step 1.

Each send-back raises a defect's `kickbacks`, and a defect stops at `fix.max_kickbacks`. A defect waits at most `fix.max_kickbacks` times, and each wait past that raises its `kickbacks`. Both counts are capped, so the loop ends for every defect but the suite's. A suite defect has no cap: it ends when its test passes, at `verified`, or when a verifier agrees that only a change to what the corpus commits to meets its test, at `promised`. The scenario its test checks still stands in the corpus, so a passing test exists.

In `sprint` mode, when the loop ends, run the checks once more: `review checks --base <the base commit> --sprint <the sprint's path>`, and drain. For each file that fails now, file a `stuck` defect: `tasks item add --pool defects --key gate --state stuck --field entry=M1 --field site=<the file> --field 'files=["<the file>"]' --body "<the check; the output>"`. `review certified` excuses a failing check only on a file a stuck defect names in its `files` or `site` field. The loop does not reopen. No fix of its own changed a file, so nothing is restored, and the owner list files it as a judgment issue as it stands.

## What the run leaves for the owner

Before the return, file one last task: `tasks file --role report --prompt owner-list --agent ok-opus --key gate --files .ok-planner/issues.jsonl .ok-planner/history/issues.jsonl --brief "run <the run's name>"`, and drain it. The owner list writes the intake through `.ok-planner/bin/issues` alone and names each issue by its id. It files the defects outside the run's reach as `category: defect` issues. It files every harm whose fix lies in a part the project does not own as a `category: upstream` issue, and every stuck defect and every other item that needs the owner's judgment as an issue in any other category but `defect`; it files one `product-intent` issue per `promised` defect, the change to what the corpus commits to that its test waits on; a stuck defect that came from a defect issue turns that issue into a judgment issue. It closes each defect issue the run fixed or found gone, or declined with a reason a verifier accepted, per the Defect issues section of `.claude/rules/ok-planner-cheatsheet.md`. Every mode files the same way.

Where the owner list wrote or turned any issue, run `/triage-issues` next, before the return. It closes a defect the code no longer shows and a question the corpus or the tooling already answers, retires a defect claim no accept-list entry covers, marks a code-only fix `category: defect` for the next run, leaves each upstream issue open for the next `/plan-sprint` with a draft ready to file, and writes a generated or recommended ruling on each other judgment issue. It skips every issue already routed or ruled by the owner, unless the owner left a message on it that triage has not yet seen. `/triage-issues` opens a ledger of its own, which moves the tracker's pointer off this run's ledger. Once it returns, select this run's ledger again with `tasks use .ok-planner/review/runs/converge-<date>T<time>.jsonl`, so every `tasks` and `review` call after it reads this run: the session notes, `review drives --confirm --dry-run`, and the return's `tasks calls`, `tasks status`, and `tasks report`.

The session records its own observations as items the moment it has them, never at the end from memory: `tasks item add --pool calls --key gate --field kind=session-note --field topic=<accept-..., prompt-..., tool-..., product-...> --body "<the observation, with the task ids and sites it rests on>"`.

## Calls

| kind | who writes it | who reads it |
|---|---|---|
| `question` | a merge agent, a fixer, or the sprint alignment pass, for what the product owes and the corpus does not decide | the owner-list agent, into the intake |
| `noticed` | a fixer, for a defect outside its brief | the owner-list agent, into the intake as `category: defect` |
| `proposal` | any agent, for a harm the accept list does not name | the owner-list agent, into the intake as `category: upstream` with a `## Proposed entry`; `/triage-issues` judges it against the accept list as it stands, routes a covered harm `defect`, and leaves an uncovered one open for `/plan-sprint` |
| `session-note` | the session, about the accept list, the prompts, or the tool | the owner-list agent, into the intake as `category: upstream` where the change lies in a file the suite owns, and as `category: tooling` where it lies in the project's own tooling or environment |
| `unlisted` | a sprint pass, for a behavior change the notes do not list that meets every user's goal | the completion report's calls table, for the owner's veto |
| `untested`, `departure`, `scope`, `mechanics` | a test stage's test support, test, legacy, sweep, or preflight task, for a choice the scenario definition, the plan, and the test rules do not decide | the completion report's calls table, for the owner's veto |
| `call`, in the `divergences` pool | a test verifier, for each resource declaration it accepts | the completion report's calls table, for the owner's veto |

Check the table against the prompts when either changes: `grep -o -- '--field kind=[a-z-]*' .claude/skills/converge/prompts/*.md | sort -u` lists every kind a prompt writes.

## The return

The run ends by presenting one block.

- `mode`: `drive`, `analysis`, `defects`, or `sprint` with the sprint's path and base commit.
- `hunt`: in `drive` mode, "the project has no story" where step 1 of the shared drive text skipped the drive; otherwise the set the drive took, every story in `drive` mode, and in `sprint` mode the sprint's new and changed stories or every story, as the testing state picked it, then the stories tried and each one's outcome (`achieved`, `failed`, `stuck`, `blocked`) per surface and variant, and the failures sorted `defect`, `not-owed`, `environment`, `redrive`, `judgment`, `upstream`, `rejected`, and, in `sprint` mode, `backlog`. In `analysis` mode, per area: hunts run, defects, the latest hunt's new count, the estimate of defects not yet found, and how the area stopped; then the totals, and the areas with the largest estimate still missed; and, where the run cut no flow area, the note `review areas` printed. In `drive` and `sprint` mode, also each `stack-stop`, `instance-destroy`, or `resource-stop` task that failed after a drive or a confirm round, with its output tail; each start that failed, with the first word and the cause of its `drive-start` result; where the drive ended without driving, the cause and every story it did not drive; and each story driven again one driver at a time after the shared stack broke, with its outcome, and each story the fallback did not drive again. In either, and in `defects` mode, the backlog: issues taken up, merged, found gone, and found to name only files the run leaves alone. In every mode, each merge that closed unfinished twice, with the reports and failures it left `open`.
- `sprint`, in `sprint` mode: one line per work item and taken improvement, with its entry point from the close result of the review root that finished, and whether it works end to end; the behavior changes judged, counted by ruling, and how many became defects; the set the drive took, the sprint's new and changed stories under `on` or `frozen` or every story under `off`, and the stories driven, with each one's outcome per surface and variant; where the set was empty, that the sprint names no new or changed story; or, where the drive did not run, why, and that the completion contract stays open; the checks and their final result; the reports sent to the intake as outside the sprint's scope.
- `deltas`, in `sprint` mode: one line from what `review deltas --sprint <the sprint's path>` prints, `<n> compared, <n> landed at build, <n> landed by this run (<each artifact>), <n> stuck (<each artifact>)`; then each delta it lists as unsettled, with why, and each C3 defect it lists as unmatched.
- `suite`, in `sprint` mode: where the testing state is `off`, that the suite was skipped under `off`. Otherwise the state; each whole-suite round, with its number and its count of failing tests, and the count of tests rerun alone after it, with how many failed again; the reports `tests reports` added, by class T1 to T4, with the failures already reported and those a hold settles; the speed tasks each speed step filed and their verdicts, and each round that filed no speed step because its only failures were schedule pairs or a failed setup; the test tasks and test support tasks the test stages filed, and each refusal of the write stage; each `exec` task of the suite that failed, with its output tail; and the final round's `tests settled` line, with each product-slow verdict it lists as deferred to the intake.
- `fixed`: defects `verified`, `declined`, `duplicate`, `promised`, and `stuck`, and any still `promise`, `at-fault`, or `rewrite`, by entry of the accept list or sprint class, and each `stuck` defect also by its item id in the run's `defects` pool, such as `i2`; the fix rounds run; the send-backs, by defect; the waits, by defect, listed apart from the send-backs; and, in `drive` and `sprint` mode, each verified defect still unconfirmed at the end, with each folded duplicate its entries name, as `review drives --confirm --dry-run` lists it.
- `calls`, in `drive`, `analysis`, and `defects` mode: what `tasks calls` prints, one row per decline, duplicate, `not-owed` or rejected failure, and rejected report, with its site and choice. In `sprint` mode the return lists no calls: the completion report's calls table carries them, for the owner's veto.
- `ledger`: the ledger's path; the run's folder stands beside it.
- `intake`: every issue the owner list wrote, turned, or closed, by id, with its category; each stuck defect by that id, with its last verifier's note and its restoration's outcome: the accepted restore task, `stuck` with the state the code was left in, or none where no fix changed a file; every `environment` failure; every report and failure the merge set to `judgment` or `upstream`, with its file, its kind, and the issue the owner list wrote for it; every report and failure the merge rejected as a record, with its file. Where any issue was written, the `/triage-issues` report: the issues it closed or retired, and each route and ruling it wrote.
- `cost`: the usage `tasks status` totals and the task count from `tasks report`.

In `drive`, `analysis`, and `defects` mode, the block is the whole report, and every question the run raised is already in the intake for the next `/plan-sprint`. Present the `calls` rows to the owner and, beside the offer below, ask which rows, if any, the owner vetoes. Where `tasks calls` printed `None.`, ask nothing beyond the offer. For each vetoed row, file one issue with `.ok-planner/bin/issues file --from -`, in the format of the `{{ISSUE-FILE-FORMAT}}` block of `.claude/skills/_shared/artifact-definitions.md`: kind `human`, category `product-intent`, its problem the row. Then record the owner's words as that issue's ruling with `.ok-planner/bin/issues rule <id> --text -`, the words on stdin, so the next `/plan-sprint` pulls the veto in as the owner's decision. `issues rule` signs the ruling with the name of the person running the session; where it refuses for want of a name, relay the refusal's setting text to the owner and record the ruling once a name resolves. End the report with one offer, to archive and commit the run: the fixes, `.ok-planner/review/rotation.json`, the ledger, the run's folder, and the intake's two files, `.ok-planner/issues.jsonl` and `.ok-planner/history/issues.jsonl`, where the owner list or a veto changed either, staged by name. Commit only on the owner's word. Do not push.

In `sprint` mode, the return is the run's last act: the sprint's execution boilerplate writes it into the completion report, runs `review certified --sprint <the sprint's path>`, which checks the completion contract against the repository and prints `SPRINT COMPLETE` or `SPRINT NOT COMPLETE`, presents that report and its calls for the owner's veto, and offers the archive and the commit only where `review certified` printed `SPRINT COMPLETE`. On `SPRINT NOT COMPLETE`, after the veto, it writes the stop record `<stem>-stopped.txt` beside the sprint, naming each failure, and runs `review certified` again, which, while the record stands, prints `SPRINT STOPPED` with the record's reason and checks nothing else, which meets the goal's condition; the stop is no success, and the owner takes up the reason. The block asks the owner nothing: every defect the run could not fix and every question it raised is already in the intake.

## What stays outside this skill

- No agent edits a file of the four kinds the fix line rule leaves alone: the design corpus, the coding standards, the docspecs, and the surface intent; a file the suite owns; the harness settings; and a record. There are three exceptions: the owner-list agent writes the intake; a restorer returns the files a stuck defect's own fixes changed to their prior behavior, a file the fix line rule leaves alone included; and in sprint certification a C3 fixer lands a delta of the certified sprint that execution missed, copying the delta's body into the artifact or deleting the retired file and regenerating the catalog TOCs and the docspec index. Beside the owner-list agent, the session writes the intake once: at the close of a `drive`, `analysis`, or `defects` run, it files one issue per call the owner vetoes, as The return says. No agent edits prose the prose scope rule leaves out of review.
