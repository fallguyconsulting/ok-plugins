# The drive

The drive's steps, which `/drive`, `/converge` in `drive` mode, and sprint certification (`/converge sprint <path>`) run by path. The drive tries stories and fixes nothing: what a caller does with the failures its merge keeps is the caller's. Every task and item the drive files goes into the caller's ledger, under key `gate`, and every line these steps say to put in the return goes into the caller's return.

There is no plan. Each story of the set the caller names is tried once, by its own driver, as a user would try it: the driver reads "As <role>, I want <capability>, so that <benefit>" and works out from the product itself how to get the benefit, on every surface the story is offered through, the primary surface `.ok-planner/review/project.md` names first. On each surface it drives every variant the story's own text names, each way the story says its benefit comes, and judges each variant on its own, as it judges each surface. It starts each surface as a first-time user would, taking first the action a new user takes first, and its close result lists each variant it drove per surface, so the merge sees what a pass covers. Nothing about the drive is written down between runs, so nothing breaks when the product changes.

**The story set.** The caller names it, and steps 1 and 3 take it:

- every story under `.ok-planner/design/stories/`: `review stories` and `review drives`, with no `--sprint`;
- a sprint's new and changed stories: `review stories --sprint <the sprint's path>` and `review drives --sprint <the sprint's path>`. The set is every story a `### New story:` or `### Amend story:` delta of the sprint names, and every `story:<slug>` its `## Work items` section names whose story file exists.

**The merge rule**, which every merge of the drive obeys: a `merge` task that closes with any outcome but `done` is refiled once with `tasks refile <task>` and drained. After a second such close, name the merge in the return. Every failure its brief names that still stands `open` goes to the owner list, which files it as a defect no merge agent judged.

1. **The stories.** Run `review stories` in the form the caller names. It lists each story of the set by slug. Where it prints no slug, the set is empty: skip steps 2 to 6, and say so in the return, that the project has no story, or that the sprint names no new or changed story. The drive then ends.
2. **The stack.** `tasks round start`. `review drive-stack` reads the `## Drive commands` section of `.ok-planner/review/project.md` and prints one word on its first line. `unfilled`, or a refusal because the section is missing or declares no stack beside a stack line: the drive cannot start: say so in the return, with the reason `unfilled` prints on its second line or the refusal, and the drive ends. `none`: the project declares that the product has no stack, so skip this step, step 4's stack stop, and step 5's start and stop, and go to step 3. `stack`: file one `exec` task that starts the stack with the command the section gives, and drain it. File every `exec` task of the drive with its role's command substituted whole, so the shell that files the task expands nothing in the line: `tasks file --kind exec --key gate --command "$(.ok-planner/bin/review drive-command --role stack-start)"`, with the role and the options each step names in place of `--role stack-start`. The drive runs a stack of its own, as the project's facts describe it. Where the start passes, go to step 3. Where it fails, file one `drive-start` task, `tasks file --role drive-start --prompt drive-start --agent ok-opus --key gate --brief "start task <the failed exec task>; start <n> of 3"`, and drain it: its agent reads why the start failed and changes nothing. Act on the first word of its result alone. On `held` or `retry`, `tasks refile <the failed start task>` and drain it. On `own`, file and drain the `stack-stop` task in this step's form, then refile the start task and drain it. On `blocked`, the drive ends. A refiled start that fails goes through the same sequence, with at most 3 starts in all, the first and two more, whatever each verdict was. A `drive-start` task that closes with any outcome but `done` is refiled once; after a second such close, the drive ends, and the session records the failure itself: `tasks item add --pool failures --key gate --state environment --fingerprint "stack-start-<the start task>" --field surface=stack --field result=blocked --field start=<the start task> --body "<the start command>; exit <code>; saw: <the start's output tail>; cause: the drive-start task closed <outcome> twice"`. Where the drive ends, say so in the return with the cause the last `drive-start` result names, and name every story step 1 listed as not driven. File no `stack-stop` task then: a start that fails takes down what it opened, and a start refused because a run holds its name opened nothing, so a stop line run then would take another run's stack down.
3. **The drivers.** Run `review drives` in the form the caller names. It files one `drive` task per story of the set. Drivers share the stack and run together, each in a browser context of its own. The verb gives every brief a drive name, unique to the run, the round, the story, and its ordinal, and lists it as `name` in its output; a driver whose story needs a resource of its own starts it under that name, as the project's facts say, and stops it at the end, beside the other drivers. `.ok-planner/review/project.md` names two lists, and the verb refuses a story named in both. A story under "Stories that drive on an instance of their own" drives on a throwaway instance: the verb files it unchained, names a folder under the system temp directory in its brief, unique to the run, the round, and the story, and lists that folder as `instance` in its output. A story under "Stories that drive alone" changes state every driver reads, so the verb files it after every other driver and the alone story before it. Where the instance list holds the line `- One at a time`, the verb chains each instance story instead: it files it last, after every driver already filed, the alone stories and the instance story before it included, so at most one instance runs beside the shared stack. Drain under a cap of **8**. A driver that closed `partial` is refiled once with `tasks refile <task>`; after a second, its story is named in the return.
4. **Stop the stack.** Whether or not its driver finished, file one `exec` task per `instance` folder `review drives` listed, with what `review drive-command --role instance-destroy --folder <folder>` prints, and one `exec` task per `name` it listed, with what `review drive-command --role resource-stop --name <name>` prints, and drain them: they stop what a driver that ended early left running. Then, where `review drive-stack` printed `stack` and step 2's start passed, file and drain one `exec` task whose `--command` is what `review drive-command --role stack-stop` prints. Step 2 gives the form that files each of these tasks. The stack stops last, so a line that reaches the running stack still finds it. A `stack-stop`, `instance-destroy`, or `resource-stop` task that fails is named in the return with its output tail, and the drive goes on.
5. **One driver at a time.** Run `tasks item list --pool failures --key gate --state redrive --json`. Where it lists no item, go to step 6. Otherwise the shared stack broke while drivers ran together, and step 4 has already stopped it. Where the drive has a stack, start it again as step 2 does, with a fresh budget of 3 starts. Where that sequence ends the drive, name each story whose driver the items name as not driven again, file no stop, and go to step 6. Then refile each driver task the items name, once each, in the order the items list them: `tasks refile <task> --brief "<its brief>; one at a time" --after <the refile filed before it>`, the first with no `--after`. Drain under a cap of **8**. A refiled driver that closes `partial` is refiled once more, as step 3 says. Then stop what this step started, as step 4 does, in its order, over the `instance` folders and `name`s step 3 listed for those drivers, with the `stack-stop` last where this step's start passed. A driver whose brief says `one at a time` records a broken stack as a `blocked` outcome at `open`, so this step runs once per drive and its outcome reaches the merge.
6. **The merge.** `review merges --source drive` files one `merge` task per `hunt.merge_reports` of the open failures. Drain under a cap of **8**, under the merge rule. Each sorts its failures as `defect`, `not-owed`, or `environment`, and folds the defects into the list. A caller that merges other findings in the same step, as sprint certification does, files this step's merges beside its own and drains them together.

The drive ends after one attempt per story.
