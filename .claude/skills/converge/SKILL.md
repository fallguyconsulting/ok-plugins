# Converge (find, then fix)

The run's estate is `.ok-planner/review/`: the catalogs under `catalog/`, the project's settings in `config.json`, the project's facts in `project.md`, and one ledger and folder per run under `runs/`.

**The run finds, then fixes.** It runs two loops, one after the other, and each one ends on its own terms:

1. **Find.** The mode decides how the run finds defects, and a merge agent folds every report into one defect list.
   - In `drive` mode the finders are drivers, one per story, each trying once to get what its story promises by using the product. Where a story is offered through a skill, its driver reviews the skill text against the story instead.
   - In `analysis` mode hunters read the code: each area at least twice, file areas through two lenses of the accept list (`failure`: A3, A4, A5, A9; `state`: A1, A2, A6, A7, A8) and flow areas along each public entry point's path, and at most a set number of times, and hunting stops per area when a hunt adds few new defects relative to what the area has shown. Each run hunts one slice of the areas and finishes it whole; the next run takes the next slice.
   - In `sprint` mode, sprint certification, the run certifies one executed sprint: one review of the sprint's change for completion and regression, the project's checks over the changed files, and a drive of the stories the sprint adds or amends. The review's reading fixes the run's scope.
   - In `defects` mode the run finds nothing new: the defect backlog is its whole input.
   - `drive`, `analysis`, and `defects` mode take up the defect backlog: every `category: defect` issue in the intake that no sprint has promoted becomes a report.
2. **Fix and verify.** Fixers work through the defect list once. Verifiers read only the change each fixer made. A fix a verifier sends back is fixed again, until none is sent back or a defect reaches its limit of send-backs. A defect at its limit is stuck: an agent backs its change out of the tree, and it goes to the intake as a judgment issue.

Neither loop re-hunts code a fix changed. New code a fix adds is checked by its verifier against the accept list and the release boundaries, and the next run's hunt reads it as ordinary code. That is what keeps the run finite: the old loops re-read every file a fix touched, and every re-read found something new in the code the last fix had added.

**The accept list decides what is a defect.** `.ok-planner/review/catalog/accept.md` names the harms the run fixes: stored state left half-changed, a write on the wrong target, an end user able to break the product, a unit of work ending with no record, ongoing work that stops or wears down, access granted or kept wrongly, accepted data lost, skipped, or doubled, code that breaks a rule the project states where the rule decides the fix, and a report that tells someone something false. Every finder, merge agent, fixer, and verifier reads it. A site the list does not cover stands. `.claude/rules/plumbline-coding.md` governs catches: a library's error that reaches the owner frame is not a defect. In `sprint` mode the sprint's own promises count too, under the sprint catalog `{{SPRINT-CATALOG}}` in `.claude/skills/_sprint/shared.md`.

**Release boundaries bind every fix.** `.ok-planner/release-boundaries.md` names the users that do not update when the code does, and stored state is always one. A fix keeps them working unless a ruling of the sprint in scope allows otherwise.

**The intent is to fix, not to file.** Every defect on the list is fixed in the run, declined with a reason a verifier accepts, or stuck. A stuck defect's fix failed twice, so what fixes it is a judgment: its change is backed out and it becomes a judgment issue. What the run meets outside its scope goes to the intake, per the Defect issues section of `.claude/rules/ok-planner-cheatsheet.md`: a defect the accept list decides becomes a `category: defect` issue, for the next `drive`, `analysis`, or `defects` run; anything that needs the owner's judgment, about the product or about the project's own tooling, becomes an issue in any other category, for the next `/plan-sprint`. A harm whose fix lies in a part the project does not own — a file the suite owns, such as this skill, its prompts, or the catalogs; a library the project depends on; an outside tool or service; or the accept list itself, for a harm it does not name — becomes an upstream issue in the intake, `category: upstream`, with a draft ready to file, for the next `/plan-sprint`. The run asks the owner nothing about it.

**The run leaves the owner nothing to settle.** It ends with every fix it kept verified, every change it could not verify backed out, and everything else in the intake. The owner reads a report and decides whether to archive and commit.

Every mechanical step is a verb of `.ok-planner/bin/review` or an `exec` task. Every agent is a task in the task tracker at `.ok-planner/bin/tasks`, drained by the drain loop at `.claude/skills/_tasks/drain.md` under a vendored profile, or a fork of the sprint review root. The skill dispatches no agent directly. The session reads no file for judgment and edits no file but the run's ledger.

## Scope

**Every file the project owns, by ownership, not location.** A run fixes a clear defect in every file the project owns, wherever it sits, under `.claude/` and `.ok-planner/` too. It leaves five kinds of file alone: the design corpus and the coding standards, which change only through a sprint's deltas; a file the suite owns, whose harm goes to the intake as an upstream issue; an owner's declaration (the project's configuration, harness settings, review facts, release boundaries, surface intent, and document types), whose defect goes to the intake as a judgment issue; a record, which changes only through the act that owns it and about which the run files nothing; and a document the release regenerates, left to `/document`. `review owner <path>...` prints each path's kind: `project`, `suite`, `corpus`, `declaration`, or `record`. `{{FIX-LINE-RULE}}` in `.claude/skills/_converge/coding-rules.md` states the rule every merge, fix, verify, backout, sprint review, and sprint pass prompt carries.

**Code, and skill text.** The analysis hunt reads code alone: `review files` lists its population: every tracked or untracked file under the project root and under each folder `.ok-planner/config.json` declares under `folders` that is not prose (`.md`, `.markdown`, `.rst`, `.txt`), not binary, not at a test path, not a file `review owner` classes as anything but `project`, and not under an excluded path in `.ok-planner/review/config.json` (the paths the project adds).
Nothing here adds, edits, runs, or reads a test.
In `sprint` mode the sprint's alignment pass reads the design corpus under `.ok-planner/design/` to compare it with the sprint's deltas. Skill text is code: a prompt an agent session runs in the project, whether the product ships it or the project keeps it for its own work, such as a skill, a rule, or an agent profile. A driver reviews a story's skill surface, the sprint review reads skill text the sprint's change reaches, a defect issue may name it, and fixers fix it as code. Other prose is in review only where the sprint the run certifies added or changed it. `{{PROSE-SCOPE-RULE}}` in `.claude/skills/_converge/coding-rules.md` states the rule every merge, fix, verify, sprint review, and sprint pass prompt carries.

**The invocation** takes optional arguments, in any order:

- `drive`, `analysis`, `defects`, or `sprint <path>`: the mode, and for `sprint` the sprint's path under `.ok-planner/sprints/`.
- `--only <path or glob> ...`: in `analysis` mode, hunt only the file areas holding a matching file and the flow areas whose declaring file matches. It limits the hunt alone: a fix reaches every file it needs.

**Ask for the mode.** Where the invocation names no mode, ask the owner before anything else, in one plain-text line, not a form: `Drive (the default) or analysis?` Wait for the answer. An answer that names neither, or accepts the default, means `drive`. `defects` and `sprint` mode are named, never defaulted to.

**Where it runs.** On the branch the working tree has checked out. A working tree with a merge in progress (`git rev-parse --verify --quiet MERGE_HEAD` resolves) is refused. Uncommitted work that stands before the run is left as it stands: agents stage by name and never discard.

## Setting up the run

1. **Preconditions.** `.ok-planner/bin/tasks`, the profiles under `.claude/agents/`, and `.ok-planner/review/` with its `config.json`, `project.md`, and `catalog/accept.md` exist; otherwise say which is missing and stop. Run `.ok-planner/bin/issues list`. It writes a note on stderr for each markdown issue file or stray line it skips; say each note in the return, and go on. In `sprint` mode, read the sprint's base file (beside the sprint, `-base.txt` in place of `.md`); where it is missing, ask the owner once for the base commit and write the file from the answer. The sprint's build run file (`-run.jsonl` in place of `.md`) is read where it exists; a sprint built without one has no build divergences or noticed defects, and says so in the return. Say the run's shape in one line before it starts: the mode; for `defects` the count of `category: defect` issues it takes up; for `analysis` the count of file areas and flow areas, the hunt settings (`min`, `max`, `threshold` from `config.json` `hunt`), and any `--only` limit; for `sprint` the sprint, its base commit, the count of changed files and stories, the paths outside the project root it lists, and whether a build run file exists. The changed files are what `review changed --base <base>` lists: every file added, changed, or deleted since the base under the project root and its declared folders, untracked files included, relative to the project root, less the files `review owner` classes as anything but `project` (so a changed declaration, corpus file, or record is not on the list) and the paths `.ok-planner/review/config.json` lists under `exclude` and `test_patterns`. In `sprint` mode every `review changed`, `review checks`, and `review snapshot` call adds `--sprint <the sprint's path>`, so the list also holds the files changed under each folder the sprint lists under `## Paths outside the project root`, as paths relative to the project root, such as `../runtime/build`. `review checks` runs each check over the added and changed ones.
2. **Open a fresh ledger.** `tasks init converge-<date>T<time> --file .ok-planner/review/runs/converge-<date>T<time>.jsonl`, the timestamp from `date +%Y-%m-%dT%H%M%S`. Never `tasks use` an existing file. The run's folder is `.ok-planner/review/runs/converge-<date>T<time>/`.
3. **Register the profiles**: `tasks agent register ok-opus`, and in `sprint` mode `tasks agent register ok-review`.
4. **Assemble and register the prompts**, each written into the run's folder by `review prompt --name <name> --out <folder>/<name>.md` and registered with `tasks prompt register <name> <path>`: `merge`, `fix`, `verify`, `backout`, and `owner-list` always; `drive` in `drive` and `sprint` mode; `hunt-file` and `hunt-flow` in `analysis` mode; `sprint-review` and `sprint-pass` in `sprint` mode. In `sprint` mode every `review prompt` call adds `--sprint <the sprint's path> --base <the base commit>`, so every prompt names the sprint whose rulings bind the fixes.
5. **Declare the vocabulary**: `tasks config set item_states '{"reports": ["open", "merged", "rejected", "backlog", "judgment", "upstream"], "defects": ["open", "fixing", "fixed", "declined", "duplicate", "verified", "stuck"], "failures": ["open", "defect", "not-owed", "environment", "backlog", "judgment", "upstream", "rejected"], "merges": ["done"], "calls": ["open", "promoted"]}'` and `tasks config set swept_roles '["fix"]'`. Every task carries key `gate`.

## Loop 1: find and merge

### The backlog, in drive, analysis, and defects mode

Before the hunt, take up the intake's defect issues: every record in the live store, `.ok-planner/issues.jsonl`, with `category: defect` whose state is `open` or `verified` and whose `sprint` is not set, read through `.ok-planner/bin/issues`. A record whose `sprint` is set is promoted into that sprint and waits for its archive step, so the backlog leaves it alone. `review backlog` adds one report per issue: its `problem` as the body, its id in the `issue` field, the first `path:function` its problem names as the site, and every file its problem names that the run may edit. It works out every issue's report before it adds any. An issue whose problem names no file the run may edit adds no report: the verb lists it under `settled`, with `files: []` and each file it names that the run leaves alone, with its kind, under `left_alone`. For each settled issue, add its report yourself, so the merge agent routes it:

- Where `left_alone` names files, the ownership test routes it: `tasks item add --pool reports --key gate --field area=backlog --field hunt=1 --field issue=<the issue id> --field site=<its first left-alone file> --field 'files=[<its left-alone files>]' --body "issue <the issue id>: its problem names only files the run leaves alone: <each file and its kind>"`.
- Where `left_alone` is empty, the problem names no file of this tree outside the exclude list, and the report names no site: the merge agent finds the site the problem describes, or finds the defect gone: `tasks item add --pool reports --key gate --field area=backlog --field hunt=1 --field issue=<the issue id> --field 'files=[]' --body "issue <the issue id>: its problem names no file of this tree outside the exclude list"`.

A store that does not exist yet is an empty backlog. Where the backlog holds any report, `review merges --source backlog` files one `merge` task per `hunt.merge_reports` of them; drain. The merge agent checks each against the code and merges the real ones, each carrying its issue's id.

In `defects` mode this is the whole of Loop 1. Where the intake holds no such issue, say so and end the run.

### In drive mode

There is no plan. Each story under `.ok-planner/design/stories/` is tried once, by its own driver, as a user would try it: the driver reads "As <role>, I want <capability>, so that <benefit>" and works out from the product itself how to get the benefit, on every surface the story is offered through, the primary surface `.ok-planner/review/project.md` names first. Drive mode takes every story every run: it is where the run spends its tokens. Nothing about the drive is written down between runs, so nothing breaks when the product changes.

1. **The stories.** `review stories` lists every story by slug.
2. **The stack.** `tasks round start`. `review drive-stack` reads the `## Drive commands` section of `.ok-planner/review/project.md` and prints one word. `unfilled`, or a refusal because the section is missing: the drive cannot start: say so in the return, with that reason, and go to Loop 2 with what the list holds. `none`: the project declares that the product has no stack, so skip this step and step 4's stack stop, and go to step 3. `stack`: file one `exec` task that starts the stack with the command the section gives: `tasks file --kind exec --key gate --command "<what review drive-command --role stack-start prints>"`, and drain it. The drive runs a stack of its own, as the project's facts describe it. Where it fails, the drive ends: say so, with the output tail, and go to Loop 2 with what the list holds.
3. **The drivers.** `review drives` files one `drive` task per story. Drivers share the stack and run together, each in a browser context of its own. The verb gives every brief a drive name, unique to the run, the round, the story, and its ordinal, and lists it as `name` in its output; a driver whose story needs a resource of its own starts it under that name, as the project's facts say, and stops it at the end, beside the other drivers. `.ok-planner/review/project.md` names two lists, and the verb refuses a story named in both. A story under "Stories that drive on an instance of their own" drives on a throwaway instance: the verb files it unchained, names a folder under the system temp directory in its brief, unique to the run, the round, and the story, and lists that folder as `instance` in its output. A story under "Stories that drive alone" changes state every driver reads, so the verb files it after every other driver and the alone story before it. Drain under a cap of **8**. A driver that closed `partial` is refiled once with `tasks refile <task>`; after a second, its story is named in the return.
4. **Stop the stack.** Where `review drive-stack` printed `stack`, file and drain one `exec` task whose `--command` is what `review drive-command --role stack-stop` prints. Then, whether or not its driver finished, file one `exec` task per `instance` folder `review drives` listed, with what `review drive-command --role instance-destroy --folder <folder>` prints, and one `exec` task per `name` it listed, with what `review drive-command --role resource-stop --name <name>` prints, and drain them.
5. **The merge.** `review merges --source drive` files one `merge` task per `hunt.merge_reports` of the open failures. Drain under a cap of **8**. Each sorts its failures as `defect`, `not-owed`, or `environment`, and folds the defects into the list.

The loop ends after one attempt per story.

### In analysis mode

1. **The slice.** `review areas --out <folder>/areas.json`. It groups the code files by directory into file areas of about `hunt.area_lines` lines, one area for each lens in `hunt.lenses`, and the public entry points the surface extraction lists (the kinds in `hunt.flow_kinds`) into flow areas of `hunt.flow_area_size` each, grouped by the file that declares them. Then it takes this run's slice: `hunt.slice` areas, file and flow areas in turn, those never hunted first, then those whose files changed since their last hunt, then those hunted longest ago, by the stamps in `hunt.rotation`. The run finishes its slice whole; the next run takes the next slice. Where the extraction is missing, it says so and the run hunts file areas alone; say so in the return. `--only` replaces the slice with the areas it matches.
2. **The first hunt round.** `tasks round start`. `review hunts --areas <folder>/areas.json --first --out <folder>/round-1.json` files hunts 1 and 2 of every area: a `hunt-file` task for a file area, whose brief names its lens and files, and a `hunt-flow` task for a flow area, whose brief names its entry points. Drain under a concurrency cap of **8**. A hunt task that closed `partial` is refiled once with `tasks refile <task>`; a second `partial`, or a close at `blocked` or `disputed`, is named in the return, and its area's count for that hunt stands at what its reports show.
3. **The merge.** `review merges --round <folder>/round-<n>.json` reads the round's open reports, groups the areas whose reports touch the same files into one merge task of at most `hunt.merge_reports` reports, and files it. It writes a zero count for each area and hunt that reported nothing, so those need no agent. Drain under a cap of **8**.
4. **The tally.** `review tally`. For each area it prints the hunts run, the defects found, how many the latest hunt added that no earlier one had, a capture-recapture estimate of the defects no hunt has found yet (from hunts 1 and 2), and a decision: `hunt` while the area has had fewer than `hunt.min` hunts, `stop: converged` once the latest hunt added no more new defects than `hunt.threshold` allows (its `share` of the area's defects, or its `floor`, whichever is larger), `stop: cap` at `hunt.max` hunts. Say in one line how many areas hunt again and how many stopped.
5. **Later rounds.** `tasks round start`, then `review hunts --areas <folder>/areas.json --out <folder>/round-<n>.json`, which files the next hunt of each area the tally says to hunt, then the merge and the tally again, until no area hunts.
6. **Stamp the slice.** `review rotate --areas <folder>/areas.json` records each area's files and entry points as hunted now, at this commit, with each file's content as the hunt read it. A file a fix later changes reads as changed, so a later run hunts it again early.

Hunters never see each other's reports, and never see the defect list. Their independence is what makes the tally mean something.

### In sprint mode

`/converge sprint <path>` is **sprint certification**: the run certifies one executed sprint, and the sprint's execution boilerplate names it as the closing step. Its change runs from the commit in the sprint's `-base.txt` file to the working tree. The standard is the sprint itself: its work items, its taken improvements, its deltas, and its implementation notes' rulings, beside the accept list. The review reads once, and its reading is the run's scope: nothing found later joins the list.

1. **The review.** `tasks round start`. File the review root: `tasks file --role review --prompt sprint-review --agent ok-review --key gate --brief "review"`. Drain. The root reads the sprint, the change, and the users the change reaches; files one `sprint-pass` task per pass (completion, regression, alignment), forked from its own task; closes its task; and forks one agent per pass task in one message. A pass task the drain lists under `waiting` with `fork-of` after the root's agent returned is an orphan: `tasks retry <task>` and drain again. A pass task that closes with any outcome but `done` is retried once; a second such close is named in the return.
2. **The build's noticed defects.** Where the sprint has a build run file, `review noticed --build-run <the run file>` adds one report per `noticed` item in it, under the area `sprint-noticed`.
3. **The checks.** `review checks --base <the base commit> --sprint <the sprint's path>` files one `exec` task per check in `.ok-planner/review/config.json` `checks`, each run over the files added or changed since the base and nothing else, and prints the tasks it filed. Where no file was added or changed, it files none. Drain. For each failing file, file a report: `tasks item add --pool reports --key gate --field area=sprint-checks --field hunt=1 --field entry=M1 --field site=<the file> --field 'files=["<the file>"]' --body "<the check; the output>"`.
4. **The drive.** The sprint's stories are the stories its deltas add or amend, and the stories its work items name as made true. Where it has none, or `review drive-stack` prints `unfilled` or refuses, skip the drive, and say so in the return with the reason. Otherwise run drive mode's steps 2 to 4 over those stories alone, filing the drivers with `review drives --stories <the slugs>`.
5. **The merge.** `review merges --source sprint` files the merges of the open reports, and `review merges --source drive` those of the open failures. Drain under a cap of **8**. The merge agent merges each in-scope defect, and sets each real defect outside the sprint's scope to `backlog` for the owner list. Before the scope test, it applies the ownership test of merge step 3a to the file each fix lies in, as in every mode, even where the sprint's change edited the file or a delta names the artifact: a fix in the corpus or an owner's declaration sets the item to `judgment`, a fix in a file the suite owns to `upstream`, and a fix that lies only in a record or a document the release regenerates to `rejected`. No agent of the run edits such a file, so it gets no fix round: the owner list files a `judgment` or `upstream` item in the intake, and files nothing for a record or a document the release regenerates.

## Loop 2: fix and verify

Repeat, with `r` the fix round's number:

1. **Retire what cannot be fixed.** Every defect at state `open` whose `kickbacks` field has reached `config.json` `fix.max_kickbacks` is set to `stuck`, with the last verifier's note kept. A stuck defect's change leaves the tree: `review backouts --folder <folder>` files one `backout` task per stuck defect with no backout yet, naming every fix task that staged a change for it and, for every file those tasks staged, its blob from the snapshot of the round that first fixed it. A stuck defect no fix task changed gets none. Drain under a cap of **8**. The agent removes the defect's hunks and keeps every other defect's. A backout task that closes with any outcome but `done` is refiled once; after a second, the session names it in the return and in a `session-note`. The owner list files the stuck defect as a judgment issue.
2. **End check.** Where no defect stands at `open`, the loop ends.
3. **Snapshot.** `tasks round start`, then `review snapshot --out <folder>/fix-<r>.json`. It saves the blob of every open defect's files and every file `review changed` lists as added or changed since `HEAD`, stamped with the round. A fixer may widen into a file the snapshot leaves out; that file was unchanged when the round started, so the verbs below take its blob from `HEAD`.
4. **Fix.** `review fixes --round <r>`. It groups the open defects whose files overlap, or that a merge marked `same_as` one another, into one task, up to `fix.group_size` defects a task, chains the tasks of one overlapping group behind each other, and files every group apart from the others so they run together. Drain under a cap of **8**. A fix task that closed `partial` with a result starting `outside files:` waits for the task that held them: its fixer already widened those defects' files, so set its unfinished defects (those still `fixing`) back to `open` with `kickbacks` raised by one, and they return next round grouped with the files they reach. Any other `partial` is refiled once with `tasks refile <task>` and drained; after a second, its unfinished defects go back to `open` with `kickbacks` raised by one. Every fix task of the round closes before any verifier starts.
5. **Verify.** `review verifies --snapshot <folder>/fix-<r>.json` files one `verify` task for every fix task of the round that set any defect `fixed`, naming those defects and, for every file the task staged, its blob from the snapshot or from `HEAD`. Drain under a cap of **8**. A defect still `fixed` after its verifier closed goes back to `open` with `kickbacks` raised by one.
6. **Confirm, in drive and sprint mode.** Where this round verified any defect whose `source` is `drive`, start the stack with one `exec` task whose `--command` is what `review drive-command --role stack-start` prints, unless `review drive-stack` prints `none`, run `review drives --confirm`, which files one confirm driver per such defect, chained as drive mode's step 3 chains, with a drive name and with an instance folder where drive mode's step 3 names one, and drain them under a cap of **8**, and stop the stack the same way, with what `review drive-command --role stack-stop` prints. Then, whether or not its driver finished, file one `exec` task per `instance` folder the verb listed, with what `review drive-command --role instance-destroy --folder <folder>` prints, and one `exec` task per `name` it listed, with what `review drive-command --role resource-stop --name <name>` prints, and drain them. A driver sends its defect back when the story still cannot be got. It records no new failure: anything else it meets is the next run's.
7. Go to step 1.

Each send-back raises a defect's `kickbacks`, and a defect stops at `fix.max_kickbacks`, so the loop ends.

In `sprint` mode, when the loop ends, run the checks once more: `review checks --base <the base commit> --sprint <the sprint's path>`, and drain. A file that fails now becomes a `stuck` defect with the check's output, and the loop does not reopen. It has no fix of its own to back out, so the owner list files it as a judgment issue as it stands.

## What the run leaves for the owner

Before the return, file one last task: `tasks file --role report --prompt owner-list --agent ok-opus --key gate --files .ok-planner/issues.jsonl .ok-planner/history/issues.jsonl --brief "run <the run's name>"`, and drain it. The owner list writes the intake through `.ok-planner/bin/issues` alone and names each issue by its id. It files the defects outside the run's reach as `category: defect` issues. It files every harm whose fix lies in a part the project does not own as a `category: upstream` issue, and every stuck defect and every other item that needs the owner's judgment as an issue in any other category but `defect`; a stuck defect that came from a defect issue turns that issue into a judgment issue. It closes each defect issue the run fixed or found gone, per the Defect issues section of `.claude/rules/ok-planner-cheatsheet.md`. Every mode files the same way.

Where the owner list wrote or turned any issue, run `/triage-issues` next, before the return. It closes a defect the code no longer shows and a question the corpus or the tooling already answers, retires a defect claim no accept-list entry covers, marks a code-only fix `category: defect` for the next run, leaves each upstream issue open for the next `/plan-sprint` with a draft ready to file, and writes a generated or recommended ruling on each other judgment issue. It skips every issue already routed or ruled by the owner, unless the owner left a message on it that triage has not yet seen.

The session records its own observations as items the moment it has them, never at the end from memory: `tasks item add --pool calls --key gate --field kind=session-note --field topic=<accept-..., prompt-..., tool-..., product-...> --body "<the observation, with the task ids and sites it rests on>"`.

## Calls

| kind | who writes it | who reads it |
|---|---|---|
| `question` | a merge agent, a fixer, or the sprint alignment pass, for what the product owes and the corpus does not decide | the owner-list agent, into the intake |
| `noticed` | a fixer, for a defect outside its brief | the owner-list agent, into the intake as `category: defect` |
| `proposal` | any agent, for a harm the accept list does not name | the owner-list agent, into the intake as `category: upstream` with a `## Proposed entry`; `/triage-issues` judges it against the accept list as it stands, routes a covered harm `defect`, and leaves an uncovered one open for `/plan-sprint` |
| `session-note` | the session, about the accept list, the prompts, or the tool | the owner-list agent, into the intake as `category: upstream` where the change lies in a file the suite owns, and as `category: tooling` where it lies in the project's own tooling or environment |
| `unlisted` | a sprint pass, for a behavior change the notes do not list that meets every user's goal | the sprint's completion report, as a record |

Check the table against the prompts when either changes: `grep -o -- '--field kind=[a-z-]*' .claude/skills/converge/prompts/*.md | sort -u` lists every kind a prompt writes.

## The return

The run ends by presenting one block.

- `mode`: `drive`, `analysis`, `defects`, or `sprint` with the sprint's path and base commit.
- `hunt`: in `drive` mode, the stories tried and each one's outcome (`achieved`, `failed`, `stuck`, `blocked`), and the failures sorted `defect`, `not-owed`, `environment`, `judgment`, `upstream`, `rejected`, and, in `sprint` mode, `backlog`. In `analysis` mode, per area: hunts run, defects, the latest hunt's new count, the estimate of defects not yet found, and how the area stopped; then the totals, and the areas with the largest estimate still missed. In either, and in `defects` mode, the backlog: issues taken up, merged, found gone, and found to name only files the run leaves alone.
- `sprint`, in `sprint` mode: one line per work item and taken improvement, with its entry point from the review root's close result, and whether it works end to end; the behavior changes judged, counted by ruling, and how many became defects; the stories driven, per surface; the checks and their final result; the reports sent to the intake as outside the sprint's scope.
- `fixed`: defects `verified`, `declined`, `duplicate`, and `stuck`, by entry of the accept list or sprint class; the fix rounds run; the send-backs, by defect.
- `ledger`: the ledger's path; the run's folder stands beside it.
- `intake`: every issue the owner list wrote, turned, or closed, by id, with its category; each stuck defect with its last verifier's note and whether its backout closed `done`; every `environment` failure; every report and failure the merge set to `judgment` or `upstream`, with its file, its kind, and the issue the owner list wrote for it; every report and failure the merge rejected as a record or a document the release regenerates, with its file; in `sprint` mode also every `unlisted` call, one line each, as a record. Where any issue was written, the `/triage-issues` report: the issues it closed or retired, and each route and ruling it wrote.
- `cost`: the usage `tasks status` totals and the task count from `tasks report`.

In `drive`, `analysis`, and `defects` mode, the block is the whole report: it asks the owner nothing, and every question the run raised is already in the intake for the next `/plan-sprint`. End it with one offer, to archive and commit the run: the fixes, `.ok-planner/review/rotation.json`, the ledger, the run's folder, and the intake's two files, `.ok-planner/issues.jsonl` and `.ok-planner/history/issues.jsonl`, where the owner list changed either, staged by name. Commit only on the owner's word. Do not push.

In `sprint` mode, the return is the run's last act: the sprint's execution boilerplate writes it into the completion report, presents that report, and offers the archive and the commit. The block asks the owner nothing: every defect the run could not fix and every question it raised is already in the intake.

## What stays outside this skill

- No agent edits a file of the five kinds the fix line rule leaves alone: the design corpus and the coding standards, a file the suite owns, an owner's declaration, a record, and a document the release regenerates. The one exception is the owner-list agent, which writes the intake. No agent edits prose the prose scope rule leaves out of review.
