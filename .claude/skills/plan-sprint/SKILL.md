# Sprint Planning

`/plan-sprint` is ok-planner's planning session: an interactive session with the project owner that produces a **sprint**. A sprint is a change-order against the project's durable corpora. It holds final-form corpus deltas, the work items that realize them, the implementation notes that say what execution builds, and a fixed completion contract.

The session runs planning, the sign-off review, code planning, test planning, the owner's judgments, and a review of the implementation notes. The owner approves once, at the end. Where testing is `on` or `frozen`, test planning plans every test the sprint's work needs, and the owner approves the tests with the sprint. The implementation notes say what execution builds, which existing behaviors that changes and how each is ruled, and which improvements the sprint makes in the code it touches. A sprint planned this way breaks nothing its rulings do not allow, and leaves the code it touches better against the project's accept list.

**The artifact is a sprint, not a theme.** A sprint holds potentially disparate changes — a concept clarified, a new story, an unrelated decision retired — with no required unifying focus. Get the right items into the sprint, each stated well enough to be picked up cold. Leave staging and ordering to execution: the work items stay a flat, unordered list, and no narrative holds unrelated items together.

The machinery lives beside this body and in `.claude/skills/_sprint/shared.md`. `core.md` holds the release boundaries format, the implementation notes form, and the four subagent prompts. `sprint-document.md` holds the sprint template. `tests.md` holds the test planners' revision rule and the two test plan review prompts, and `tests-story.md`, `tests-runtime.md`, `tests-programs.md`, `tests-sort.md`, and `tests-budget.md` hold the test planner prompts. `../_shared/artifact-definitions.md` defines the corpus artifacts, the docspec, the surface intent, the delta form, and the issue record's format. A `{{TOKEN}}` names the block of that name in one of these files, and resolves only where the token stands alone on its line.

## Estate

The project root is the nearest ancestor of the working directory (itself included) holding the estate directory, never derived from `.git`. The estate is a filesystem check there:

| estate | what this session does with it |
|---|---|
| `.ok-planner/` | Required. It owns the sprint, the design corpus, the coding standards (the subject and practice collections at `.ok-planner/subjects/` and `.ok-planner/practices/`), and the issue intake. Without it, say so and stop. Where either collection is missing, say in one line that `/ok` materializes it, and skip the subject and practice steps below. It also holds the docspecs at `.ok-planner/docspec/`, one file per kind of documentation the project keeps, with their generated index at `.ok-planner/docspec.md`, and the surface intent at `.ok-planner/surface/surface.md`. Where the surface intent is missing, no element is public until a sprint's surface intent delta declares one. Where `.ok-planner/docspec/` is missing, the project declares no documentation: skip the documentation step in Reconcile. |

Where `.ok-planner/design/` does not exist, the project has no corpus yet. `/discover-design` audits the code and writes a discovery; a sprint that takes the discovery up carries its new artifacts as deltas, and execution creates the folders. Where no discovery stands, say so and point at `/discover-design`; the session may still go on to work items alone.

## Vocabulary

Read `../_shared/artifact-definitions.md` before authoring anything. Every delta drafted here must already comply with the artifact rules; the sign-off review checks exactly that. `{{CORPUS-DELTA-FORM}}` is the authority on a delta's parts.

Read `.ok-planner/practice-definitions.md` before authoring a subject or a practice. It defines what a **subject** and a **practice** are, what each body carries, and how gaps, collisions, and violations differ.

Keep two things apart: the **intake** (`.ok-planner/issues.jsonl`, one record per open issue; a closed issue's record moves to `.ok-planner/history/issues.jsonl`) holds questions; the **sprint** holds what the session commits to. Issues move from the first to the second by promotion, one-way. The defect-issue rules are in the "Defect issues" section of `.claude/rules/ok-planner-cheatsheet.md`.

## 1. Layout

`mkdir -p .ok-planner/sprints .ok-planner/history/sprints .ok-planner/history/sketches .ok-planner/history/discoveries`. Estate true-up is the front door's administration (`/ok`).

The session reads and writes the intake only through `.ok-planner/bin/issues`, the intake's one module; nobody edits `.ok-planner/issues.jsonl` by hand. Where `.ok-planner/bin/issues` is missing, say that `/ok` materializes it, and stop. Run `.ok-planner/bin/issues list`. Where it refuses because the intake holds an earlier layout, say that `/ok` converts it, and stop. It writes a note on stderr for each stray line it skips; tell the owner, and go on.

## 2. Frame

Read the intake with `.ok-planner/bin/issues list --json`: every record it prints is an open issue, and a closed issue's record sits in the archive, which Frame does not read. Each record carries its computed `state` and `unseen`, the count of people's messages triage has not yet marked seen; `.ok-planner/bin/issues show <id>` prints one record whole, its discussion included. A record whose `sprint` is set is already promoted into that sprint and waits for its archive step: leave it alone. Set the `category: defect` issues apart, and the `category: upstream` issues whose `ruling` is not set. Then split the rest:

- **Ruled**: `ruling` is set. The ruling is its author's own words.
- **Ruled by silence**: `ruling` is not set and `recommendation` is, generated or recommended, and no person's comment on the record is unseen (`unseen` is 0). The owner accepted the recommendation by leaving it standing, per `decision:intake-writers-are-gated`.
- **Unruled**: neither is set, or a recommendation stands beside a person's comment triage has not yet marked seen (`unseen` above 0). That comment holds the recommendation back: Frame treats the issue as unruled and walks it at Resolve with the comment in view.

Hold the unruled ones and the upstream ones until Resolve.

**Pull in the ruled issues first.** A ruling is the owner's decision, already made. For each ruled issue, carry the ruling's substance into the draft in final form — corpus delta, work item, or both — exactly as if the owner had just decided it live. Discuss a ruled issue with the owner only when the ruling cannot be understood; then ask about that one ruling, in prose, and record the clarified ruling in the owner's words with `.ok-planner/bin/issues rule <id> --text -`, the text on stdin, which replaces the ruling. A ruling that amounts to "drop it" is a retirement: record it now with `.ok-planner/bin/issues close <id> --as retired --reason "<the owner's reason>"`, which moves the record to the archive.

**Generated and recommended rulings ride in the same sweep.** A `recommendation` of form `generated` was written because the rules determine the resolution. One of form `recommended` is triage's judgment call, which the owner accepted by silence. Carry both like any ruling, and name each batch once, at Approval. Re-discuss one only when the owner asks. Write no `ruling` for them: a ruling is a person's alone.

**Set the upstream issues apart.** An upstream issue names a harm whose fix lies in a part the project does not own: a suite-owned file, a library the project depends on, an outside tool or service, or a harm the accept list does not name. Its answer is the owner's act, not only a ruling, so a recommendation on it does not ride the sweep: walk each at Resolve. One whose `ruling` is set is ruled, and takes the answer that ruling gives, one of the three the walk offers. A ruling that chooses a filing upstream and asks for no workaround is a choice to file, whether or not it names where the owner filed the draft; a ruling that accepts a recommendation to file is one. Where the ruling names the location, record it now as the walk's **File upstream** answer does — `.ok-planner/bin/issues close <id> --as answered --reason "<where it was filed>"` — and pull nothing into the sprint. Where it names none, the owner's ruling stands as written: ask the owner where the draft was filed, in prose, as a fact, then close the issue the same way with that location as the reason, write no ruling, and pull nothing into the sprint. Where the owner has not filed it yet, show the issue's `upstream` draft so the owner can, then ask where; where the owner leaves it unfiled, the issue stays open with its ruling, and name it to the owner in one line. A ruling that chooses a workaround rides the sweep like any ruled issue. One that chooses both a workaround and a filing is answered both ways and rides the sweep too; where its ruling names no location, ask the owner where the draft was filed, as a fact, and write the location into the work item that carries the workaround. Only a ruling that chooses neither a filing nor a workaround cannot be understood: ask the owner about it, as above.

**Offer the defect issues.** List every `category: defect` record (`.ok-planner/bin/issues list --category defect`), one line each with its site and harm. The owner picks which join the sprint; pull each picked issue in as a ruled issue, its generated recommendation becoming a work item. The rest stay in the intake for the next `/converge`. Walk none of them at Resolve.

**Set the surviving inferred rules apart.** Run `.ok-planner/bin/tests rules --json`. Each entry is a rule on the code's shape that a sprint's legacy sort ported to a project check, which the sort inferred because no document stated it, that no sprint has settled, and whose `command` still stands in `.ok-planner/review/config.json` `checks`; each names its `rule`, `check`, `command`, the `test` it was ported from, and the `sprint` that ported it. Hold each until Resolve, whatever the session kind: the owner writes it down as a practice or retires it with its check.

Then establish the session kind from the owner's opening ask; where it is unclear, ask in one prose question:

- **Intake-drain sprint** — the owner's purpose is working the intake: all of it, or a batch they name. Run the issue walk (under Resolve) over that scope now, then the dialogue (thin — the resolutions largely are the intake) and the draft.
- **Feature-work sprint** — the default. The owner brings work. The intake is not the agenda beyond the ruled sweep: go to the dialogue and the draft, then consult the unruled issues at Resolve against the drafted work.

Tell the owner the counts either way ("3 ruled issues pulled into this sprint; 2 of 4 defect issues picked; 1 upstream issue to walk; 2 inferred rules to walk; 7 unruled open, 1 of them held back by your comment — I'll check which bear on this work once we've drafted it"). The count is information, not a gate; the owner may widen scope to the whole intake.

**Offer the test work.** Where `.ok-planner/bin/tests`, `.ok-planner/bin/tasks`, or the profile `ok-opus` under `.claude/agents/` is missing, say that `/ok` materializes it, and stop. Run `.ok-planner/bin/tests enabled`. Where it refuses for want of `testing.enabled`, relay its message, say that `/ok` writes the key, and stop. It prints the testing state, which decides every test step of this session:

- `off`: the sprint plans no tests. Say so in one line. The session skips the programs at Resolve, the re-plan list in code planning, and every step of Test planning but the `## Tests` section's state line.
- `frozen`: the sprint makes no offer, and plans only the `rewrite` and `retire` items each re-planned story needs. A story the sprint's deltas add gets no tests, and joins the untested list for a later sprint under `on`. Say so in one line.
- `on`: run `.ok-planner/bin/tests offers --json`. It prints the groups of each kind `testing.offers` lists, each with its key: stale stories, untested stories, legacy folders of test files no scenario claims, and the runtime group. Show the owner one line per group: its key, its kind, and its stories with their reasons, or its folder with its count of files. Ask the owner once, in prose, which groups the sprint takes; the owner takes any group whole, or none. In the same question, offer the widen: the owner may name stories to reopen for the outcomes an earlier plan's calls left out, or ask for every story an earlier plan's calls left a path out of. Keep the taken keys and the widen answer for Test planning. Every test file of a legacy folder the sprint does not take stays as it stands, and the plan records it as kept. Where `offers` prints no group, say so in one line, and offer the widen alone.

## 3. Reconcile

Work sometimes lands outside any sprint — a hotfix, an experiment that stuck, a redesign in a session that never ran `/plan-sprint`. The corpus catches up with such work here, before the dialogue builds on it. Where Frame already drafted a delta on an artifact this phase changes, that delta is rebuilt under section 5's one-artifact-one-delta rule. This session is the one place the corpus catches up with out-of-band work; sprint certification lands only its own sprint's approved deltas. Certification cannot do this catching up, because its fixers hold the rest of the corpus fixed and would bend new code back toward stale docs.

1. **Resolve the baseline.** Every sprint whose archive-and-commit step ran carries `closed: <sha>` in its frontmatter. The baseline is the `closed:` stamp of the newest file under `.ok-planner/history/sprints/` that has one. Where none has one, say so and ask the owner, once, in prose, whether to name a baseline ref or skip the walk.
2. **Compute the window.** `git log --oneline <closed>..HEAD` plus the uncommitted tree. An empty window passes the phase silently.
3. **Filter for bearing changes.** Most of the window is ambient change touching no corpus commitment. Dispatch `{{OUT-OF-BAND-REVIEWER-PROMPT}}` from `core.md`, and take up only what it returns as bearing.
4. **Draft the bearing set as one batch, and show the owner one summary of it**, before the dialogue builds on it. Draft each `corpus` change the reviewer returns as **corpus catches up**: the out-of-band work is intended reality; draft the deltas that bring the affected artifacts into agreement with it. Where the draft already carries a delta on an affected artifact, rebuild that delta to carry both changes, under section 5's rule. The approved delta is the work's missing authorization, granted retroactively.

   Show the summary apart from the sprint's own work: one line per change, naming its commits or files, what changed, and the deltas it drafts, from the artifacts the reviewer names it would amend. Then ask the owner, once, in prose, which changes to pull out of the batch. A change the owner leaves in keeps its drafted outcome. A change the owner pulls out takes one of two outcomes, and the pick lands in this sprint:
   - **Code catches up** — the corpus's commitment stands; take the change out of its drafted deltas, under section 5's rule, and add a work item restoring the commitment.
   - **Record and defer** — the owner wants to think; take the change out of its drafted deltas, and file an issue with `.ok-planner/bin/issues file --from -` per `{{ISSUE-FILE-FORMAT}}` (kind `human`, the divergence as its `problem`). The sprint then leaves the artifacts that divergence bears on untouched.

   The reviewer also flags documentation a person edited directly, where `.ok-planner/docspec/` exists. Documentation is the files under a docspec's `## Where`. An edit in a commit that an archived documentation sprint's `closed:` stamp names, under `.ok-planner/history/doc-sprints/`, is that run's work and is not flagged. A change to what a docspec describes is not flagged either: the next documentation sprint's window finds it through the docspec's stamp. Each `documentation edited` change joins the batch, drafted as *the edit stands*: the text stays, and where the edit changed what the documentation covers, the sprint carries a docspec delta that matches it; the next documentation sprint checks its claims. Its summary line names that docspec delta, or says the edit carries none. An edit the owner pulls out of the batch takes *record and defer*: an issue records the edit, as above, and the documentation stays as it is.

   A direct edit under `.ok-planner/docspec/` or to `.ok-planner/surface/surface.md` outside a sprint joins the batch like a direct edit under `.ok-planner/design/`: it is drafted as corpus catches up, and the owner may pull it out to code catches up or record and defer.

   The reviewer also flags a broken contract: a change outside a sprint that breaks the contract of a public element, as the public surface boundary in `{{RELEASE-BOUNDARIES}}` defines it, whether or not a corpus artifact names the element. A `contract broken` change stays out of the batch: walk each with the owner, one at a time, and the owner picks one of three outcomes for it. *The break stands*: the sprint carries a surface intent delta where the element moved or left the surface, a corpus delta where a commitment changed, and a work item that lands a migration path, such as an alias, where the element's callers outside the project need one. *Code catches up*: a work item restores the contract. *Record and defer*: an issue records the break, as above.

An empty window or an all-ambient review passes in one line ("no out-of-band work since <sprint>").

## 4. Dialogue

Discuss what this sprint takes on. The owner brings goals; you bring the corpus (read `.ok-planner/design/` freely — it is the source of truth). A sketch under `.ok-planner/sketches/` the owner names as the work's source is an input to the dialogue, read in full; note which sketches the draft takes up, since Terminal archives them.

**A discovery.** A discovery under `.ok-planner/discoveries/` the owner names is the audit `/discover-design` wrote of the code and the corpus, and the work's source. Read it whole, with each body its deltas folder holds. It names the commit it audited: `git diff --name-only <that commit> -- . ':(exclude).ok-planner'`, with the untracked files, lists what changed since. Tell the owner the count in one line, and read again each body whose artifact or evidence those files bear on before carrying it; Reconcile covers the rest. Then:

- Walk each of its questions with the owner, one per turn: the artifact, what it says, what the code does, and both drafted answers. The owner picks one, or gives an answer of their own. *The corpus is stale*: carry the stale answer's delta, its body from the discovery's `answers/` folder, in place of any other delta the discovery drafts on that artifact, and merged under section 5's rule with any delta the draft already carries on it; the answer's body already carries that delta's changes. *The code is wrong*: carry its work item, and the artifact's other delta where the discovery drafts one, since those changes hold either way. On an artifact the discovery proposes, also carry a `New <kind>: <slug>` delta whose body is the wrong answer's body, from the discovery's `answers/<question>/wrong/` folder. Where the discovery holds no such body, as one an earlier release assembled holds none, draft the body with the owner; the sign-off compliance review reads it as it reads every delta.
- Carry each form-only change into the draft without discussion.
- Carry each promise change into the draft, with its work item where it names one. The owner may raise any of them here; otherwise each waits for the owner's veto at Approval.
- Carry each suggested prohibition the discovery's `## Suggested prohibitions` section lists, in a body the sprint carries, into the sign-off compliance review's `[STATED]` as a suggested prohibition with the discovery's reason. A discovery with no such section, as one an earlier release assembled, marks none: the compliance review lists each forbidding sentence in its bodies with no reason recorded.

A question the owner postpones is filed per Resolve's postponement rule, and the sprint leaves its artifact untouched.

Ask questions in prose. Surface every tradeoff explicitly, and put each one to the owner to resolve. When work implies a story- or decision-intent change, put the three options to the owner — preserve the intent, shift the intent, remove the artifact — and the owner picks.

Raise a break of a public contract when the work first asks for it. Where the owner proposes, or a drafted delta needs, a change that breaks the contract of a public element, as the public surface boundary in `{{RELEASE-BOUNDARIES}}` defines it, name the element, its callers outside the project, and the break. The owner picks one of three answers: a compatible form, such as an alias or both shapes accepted; the break, for a stated reason; or a different outcome. Write the answer into the work item, a break as `<element>: rewrite across the public surface: <reason>`, so code planning applies it to every behavior change of that element. A break code planning or the notes review finds later goes to the owner at the owner's judgments, as `{{OWNER-QUESTION-TEST}}` sends it.

Draft a story as a need, never a design: the capability reads `I want a way to <do something>`, and the benefit is an outcome a reader can settle by observing it. Concreteness is about the outcome, never about the surface. A draft that names a page, a screen, a control, an interaction, or what a screen contains is an interface specification; it fails the three tests in `{{STORY-DEFINITION}}` — need, one need, invariance — and the interface detail belongs in the work item that builds it. A draft that bundles several capabilities is factored, never trimmed: one story per need, each with the benefit it serves, and a decision for each choice the draft prescribed that has an alternative. Reaching for correct, clear, or helpful means the need is not yet named: say what the user can now do instead, per `{{STORY-DEFINITION}}`. Where a promise rests on a human discipline's judgment, write the concrete version per `{{DECIDABILITY-BOUNDARY}}`.

Draft a concept only when it passes the two tests in `{{CONCEPT-DEFINITION}}`: existence — the project narrows the noun, and the body states the narrowing — and invariance — every sentence under What it is and Boundaries holds for every product that meets the same stories, whatever decisions it makes. A noun that names a part of the product (a page, a screen, a module) is not a concept; ask what kind of thing the part embodies and draft that, or draft nothing.

## 5. Draft

Write the sprint to `.ok-planner/sprints/YYYY-MM-DD-<slug>.md` from `{{SPRINT-DOCUMENT-TEMPLATE}}` in `sprint-document.md`. Write the `## Implementation notes` section's body as the one word `pending`; code planning fills it. Where a work item changes files outside the project root at a path the owner named, list each such folder under `## Paths outside the project root`.

**Every work item changes the product**: its code, configuration, documents, or design corpus. Draft no work item that consists of using what the sprint builds; reshape it into the feature, script, or seed asset that lets a user reach the outcome. No step of execution or sprint certification waits on a person, as `{{NO-PERSON-RULE}}` in `.claude/skills/_sprint/shared.md` says. Draft no work item that needs a person, and no work item that leaves a task for the owner to perform. Where a story's benefit passes through a party outside the product, draft the work item that builds its local stand-in. A step that needs a person never takes work out of the sprint.
Draft no work item that writes a test; the sprint's test plan names every test.

The corpus deltas are the substantive body, each authored per `{{CORPUS-DELTA-FORM}}`: a complete final-form body, resolved in this session's dialogue. Edit the artifact surgically with the owner and carry the whole result. A retirement carries only its heading. Where bodies run long, put them in the sidecar folder beside the sprint (`<sprint-name>-deltas/<kind>s/<slug>.md`) and point each heading there. A discovery's deltas folder uses the same layout: copy each body the sprint carries from it into the sprint's sidecar at the same path, its `answers/<question>/` or `answers/<question>/wrong/` prefix dropped, and point the heading there. Applying a delta is updating the corpus. Docspec and surface intent deltas take the same form; their sidecar paths are `<sprint-name>-deltas/docspecs/<slug>.md` and `<sprint-name>-deltas/surface/surface.md`. Every delta but a surface intent delta makes its collection's catalog TOC (`.ok-planner/design/concepts.md`, `stories.md`, or `decisions.md`, `.ok-planner/subjects.md` or `.ok-planner/practices.md`, or `.ok-planner/docspec.md`) stale, and applying the delta includes regenerating it with `python3 .ok-planner/bin/catalog-toc`. A TOC is generated: the next run discards a hand edit.

**One artifact, one delta.** Wherever two outcomes of the session change one artifact, the sprint carries one delta for it. The outcomes are a ruled issue drafted at Frame, a promotion from the issue walk an intake-drain sprint runs at Frame, a Reconcile "Corpus catches up", a discovery's body, and a promotion at Resolve. The delta's whole body carries every change: rebuild it from the artifact as the latest outcome leaves it, never from the live file alone.

**The sprint is self-sufficient.** Once written, it is the source of truth for execution. An executing agent reads the sprint, never an issue record, to learn what a promoted issue meant: a resolution whose substance is not in the deltas or work items is not in the sprint.

**The surface.** Nothing is public until the owner declares it. A new element no rule or exception of the surface intent makes public is internal, and planning asks nothing about it; a new element of a class a rule already makes public, such as a new verb on a declared command, is public by that rule, save a gated element, one the product exposes only while a gate setting is on, an on-off setting that exists to expose debug or test elements, which stays internal until a sprint's surface intent delta names it. The surface question opens when the owner asks to make something public, and when the draft carries a `### New docspec` delta: ask the owner, in prose, what surface its documentation describes. Draft the answer as a surface intent delta in this sprint, a `### New surface intent` delta in the form `{{SURFACE-INTENT-DEFINITION}}` gives where the project has none, naming each class's declaring files. State each rule generally, such as every endpoint of one API, and name a single element only where no general rule can say it. Where a surface intent delta makes a class public that no docspec's `## Lists` names, draft a `### New docspec` delta for its reference documentation from the shape template at `.ok-planner/docs/shapes/reference.md`, as a call.

**Docspecs.** A `### New docspec` delta copies its layout lines and its `## Shape` from the shape template under `.ok-planner/docs/shapes/` that fits its kind of documentation: reference, tutorial, how-to, or overview. Propose the template, and the owner adjusts the copy; the docspec never names its template. A docspec for documentation that lives in code opens its `## Where` with `in code:` and the files whose doc comments are the documentation, and carries a `## Generator`: ask the owner for the tool. Draft no work item that writes documentation or a doc comment: a documentation sprint writes them, after the code settles, and the owner plans it with `/plan-docs`.

**Subjects and practices.** Subjects and practices are corpus deltas of the same shape as any other — new, amend, or retire, each a complete final-form body, with the sidecar available. Surface two authoring rules to the owner while drafting:

- **A subject is admissible only if its members can be enumerated.** Where the owner cannot say how a reader would list them, the artifact is not ready: say so and work out the enumeration together.
- **A departure is a competing practice, never an exemption.** Draft an exception the owner describes as a second practice over the same subject, with its own condition and its own benefit. An exception that cannot be written affirmatively is not understood yet.

The cheatsheet's universal conventions are not corpus artifacts and are never drafted as deltas.

A subject drafted without practices covering its whole population ships a gap. Name that to the owner while drafting, so the covering practices land in the same sprint or the gap is a deliberate choice. The owner decides which policies the codebase follows; draft only the subjects and practices the owner states.

## 6. Resolve

This session is the only place a judgment issue closes: **promoted** into this sprint, **retired** at the owner's word, or, for an upstream issue the owner files upstream, **answered**. The ruled ones were pulled in at Frame; this phase is the **unruled** remainder, the upstream issues Frame set apart, and the inferred rules Frame set apart, defect issues excluded. Where testing is `on` or `frozen`, this phase also asks the owner the programs questions, as "The programs" below says.

Building over an open issue decides it silently. An issue whose answer the drafted work would encode by default goes to the owner first. An issue the work neither touches nor presumes stays in the intake.

The walk is scoped:

- **Intake-drain sprint** — every unruled open issue (or the named batch), every upstream issue Frame set apart, and every inferred rule Frame set apart. Go straight to the walk.
- **Feature-work sprint** — dispatch `{{RELEVANCE-PASS-PROMPT}}` from `core.md` over the draft and the unruled open issues, then walk only the issues it returns as bearing, every upstream issue Frame set apart, and every inferred rule Frame set apart. Report the split to the owner in one line (`4 of 7 open issues bear on this work, and 1 upstream issue waits; walking those now`). The owner may pull an independent one into scope, and may leave an upstream issue open for a later session.

**Coverage questions.** A **gap** (a member of a subject no practice claims) or a **collision** (a member two equally specific practices claim under conflicting conditions) that any run or session meets goes to the intake as a judgment issue, through that run's gate. Both are ordinary intake issues, walked like any other. A **violation** is a defect: it reaches the intake as a `category: defect` issue, offered at Frame like any other.

### The issue walk

Before presenting each issue, surface the corpus that bears on it:

```bash
OK_PLANNER_PROJECT_ROOT="$(pwd)" \
  python3 .ok-planner/scripts/surface-corpus <id>
```

The script reads the record through the intake's module and prints, one per line, the concept, story, decision, subject, practice, and docspec files cited in its `artifacts` list or matching distinctive rare tokens from its id, title, problem, and options. Read each surfaced artifact in full: its Boundaries, a Choice, or a story's statement may already resolve the question, retire the issue, or reshape the framing. Where the script prints nothing, the issue is either about pure code with no corpus commitment or about a concept the record failed to name: flag it to the owner.

Walk the in-scope issues with the owner **one at a time**: present the issue's title, problem, options, and recommendation, and each person's unseen comment where its discussion holds any (`.ok-planner/bin/issues show <id>`), plus a one-sentence note on what the surfaced corpus says (`concept:X draws its boundary so the answer is Y — likely a retire`). The owner picks one of two outcomes.

**Promote** — the owner decides the answer (a candidate, or a shape of their own). Record the decision verbatim as the issue's ruling with `.ok-planner/bin/issues rule <id> --text -`, the owner's words on stdin. `issues rule` signs the ruling with the name of the person running the session; where it refuses for want of a name, relay the refusal's setting text to the owner and record nothing until a name resolves. Then carry the substance into the sprint now, in final form: corpus delta, work item, or both. On a feature-work sprint that means amending the draft, and a resolution that changes an artifact the draft already carries a delta on follows section 5's one-artifact-one-delta rule; on an intake-drain sprint these resolutions are the material the draft is built from. The sprint carries the whole resolution; the issue record is a receipt.

**Retire** — the owner drops the question ("won't fix", "not real anymore", "already answered"). Record it at once: `.ok-planner/bin/issues close <id> --as retired --reason "<the owner's reason>"`, which moves the record to the archive.

**An upstream issue** has three answers, besides a retirement. Present its `upstream` draft with it.

- **Workaround** — the project works around the harm. Promote, as above: the workaround becomes sprint work.
- **File upstream** — the owner files the draft with the ok suite or the foreign part's maintainers. Record it at once: the owner's answer in their own words as the ruling (`.ok-planner/bin/issues rule <id> --text -`, signed, or refused for want of a name, as under Promote), then `.ok-planner/bin/issues close <id> --as answered --reason "<where it was filed: the link, or the tracker and the issue's number>"`.
- **Both** — promote, as above, the ruling naming where it was filed beside the workaround.

**An inferred rule** is no issue, and has three answers. Present its rule, its check, its command, the test it was ported from, and the sprint that ported it.

- **Practice** — draft the practice delta with the owner, per `{{CORPUS-DELTA-FORM}}`, stating the rule as the owner words it, and a work item that lands it and ends with `.ok-planner/bin/tests rules take <check> --as practice:<slug>`, run after the delta is applied.
- **Retire** — a work item that removes the command from `.ok-planner/review/config.json` `checks`, deletes the check program, and runs `.ok-planner/bin/tests rules take <check> --as retired`.
- **Postpone** — record nothing: `tests rules` lists the rule again at the next Frame.

`tests rules take` runs no test, so a work item that runs it adds, edits, deletes, and runs no test. Nothing about an inferred rule goes to the intake: its record stays in `.ok-planner/test-state.json`, which only `.ok-planner/bin/tests` writes.

Every intake write goes through `.ok-planner/bin/issues`, per `{{ISSUE-FILE-FORMAT}}`. Rulings, retirements, and filings upstream are recorded when the owner gives them, at Frame or during the walk; promotions go in at Terminal, after approval. A promotion is true only once its sprint exists in approved final form, so a session that dies before approval leaves the promoted-in-spirit issues open with their rulings preserved — the correct state. Leave every issue outside the walk's scope unpromoted and unmentioned in the sprint. A question the owner postpones is filed with `.ok-planner/bin/issues file --from -` per `{{ISSUE-FILE-FORMAT}}`, with `kind: "sprint"`. A problem with an earlier sprint's decision is a new issue under a new id.

An empty intake, or a relevance pass returning nothing bearing, passes silently.

**Work added after the walk.** The walk judged the draft as it stood at Resolve. On a feature-work sprint, each work item added or reshaped after it, each amended delta, and each call the session or the code planners make goes back through the relevance pass at Approval, before the sprint is presented.

Walk each judgment finding with the owner as the judgments above are walked. A fix that changes a **Tested stories** list changes the re-plan list: Test planning re-plans it, as its "When the re-plan list changes" says. Add the review's build notes to the work items they name, under **Calls**, for the builders. The review runs again only when the owner changes a delta or a work item at Approval.

## 13. Approval

On a feature-work sprint, first dispatch `{{RELEVANCE-PASS-PROMPT}}` from `core.md` again, its scope set to the work added or reshaped since Resolve (each work item added or reshaped as a call or on a kickback, each amended delta, and each call under a work item's **Calls**, the session's and the planners'), and its issues set to the unruled open issues the walk did not take up. Walk each issue it returns as bearing as Resolve's walk does, and amend the work item, delta, or call it bears on to the owner's answer; an amended delta goes back through the compliance review, and an amended work item through code planning and the notes review. A pass returning nothing bearing passes silently.

Where the sprint takes up a discovery, list each promise change it carried from the discovery in one line, its heading and why the code settles it, and each call the discovery lists, beside the session's own calls, for the owner's veto; a vetoed change leaves the sprint, and its artifact stays as it stands. Name the generated and recommended ruling batches Frame pulled in, one line each ("3 pulled rulings are generated: <ids>; 5 are accepted recommendations: <ids> — say the word to drop any"). List the calls the session and the planners made, one line each with what decides it, and the improvements the sprint takes, for the owner's veto. Present the suggested prohibitions from the last compliance round as one list, each sentence with its delta and its reason; where there are none, say so in one line. The owner keeps or drops each. A dropped prohibition leaves the delta before approval, and the delta goes back through the compliance review. Where the sprint plans tests, present the summary that `.ok-planner/bin/tests plan --sprint <sprint> --show` opens with, `<sprint>` and `<name>` as section 10 names them: the count of scenarios per story by action, every call of kind `untested` or `departure` in full, the other calls grouped by kind, one line each, each inferred rule a port enforces, each kind and setup pair of planned tests with its count, each shared resource a planned test declares with its tests, the test stack's budget with each limit's handling, and each time control the plan builds, with its work item. Where the whole output is too long to read in the session, name `<name>-plan.md`, which Test planning wrote, for the owner to open. The owner may decline the proposed scenarios of a story the sprint's deltas add: each is a drop, and the story joins the untested list for a later sprint. Present the whole sprint for approval. It is not final until the owner approves. An owner's change at approval re-runs the steps it touches: a delta goes through the compliance review, a work item goes through code planning and the notes review, a change to the test plan is a fix to the items of the planner it touches, applied as Test planning's "Fixing a planner's items" says, after which the session assembles again and writes the new counts into the `## Tests` section, and, on a feature-work sprint, the changed work and the calls it brings go through the relevance pass as above.

Once the owner approves the final sprint, write the approval mark at the top of the sprint file, above its title, as YAML frontmatter: a `---` line, then `approved: <the output of date +%Y-%m-%d>`, then a `---` line. Write the mark there and nowhere else, and only after the owner's final yes: where the owner changes the sprint at approval, write it once the changed sprint is approved. Every executor refuses an unmarked sprint that has no base file beside it, so a draft left by a session that ends before approval never runs.

## 14. Terminal

1. **Record the promotions.** For every issue this sprint resolved — the ruled and defect issues pulled in at Frame and the issues promoted during the walk, an upstream issue answered both ways among them, its ruling or its work item naming where it was filed — stamp the record: `.ok-planner/bin/issues promote <id> --sprint <this sprint's filename>`. The record stays in `.ok-planner/issues.jsonl` until the sprint's archive-and-commit step closes it as promoted, which moves it to `.ok-planner/history/issues.jsonl`. Every promoted id also appears in the sprint's `## Intent` list.
2. **Archive the sketches the sprint took up.** For every sketch under `.ok-planner/sketches/` the owner brought into the dialogue as the work's source, move the file to `.ok-planner/history/sketches/`, per file, and name each moved sketch in one line. A sketch the sprint takes up only in part stays where it is unless the owner says to move it; a sketch nobody brought in is left alone.
3. **Archive the discovery the sprint took up.** Where the owner brought a discovery into the dialogue, move every file under `.ok-planner/discoveries/` whose name starts with the discovery's name, its deltas folder included, to `.ok-planner/history/discoveries/`: `git mv` for a tracked file, `mv` otherwise. Name the moved discovery in one line. A discovery stands until a sprint takes it up, so `/discover-design` runs again only after this step.
4. **Leave the tree ready, then hand over the goal line.** Follow `{{PLANNING-HANDOFF}}` in `.claude/skills/_sprint/shared.md`, with `<goal path>` set to `.ok-planner/sprints/<sprint-name>.md`, this sprint's filename stamped in. The line is for the owner; the sprint document does not carry it. The executing session states the goal's stop condition in its first message, as the sprint's "How to execute this sprint" section says, so the line needs nothing more.

Then stop. The approved sprint is this skill's terminal artifact, and its own execution boilerplate describes how execution works. The session writes only the sprint, its delta sidecar, `.ok-planner/release-boundaries.md`, the intake records it rules, files, closes, or promotes through `.ok-planner/bin/issues`, the sketches and the discovery it moves, and the commits the owner agreed to. Where testing is `on` or `frozen`, it also writes the test planning run beside the sprint, `<sprint-name>-test-planning.jsonl`, with its prompts, `<sprint-name>-test-planning-<role>.md`, and the plan files `tests` writes beside the sprint, `<sprint-name>-groups.json` and `<sprint-name>-plan.json`, with `<sprint-name>-plan.md` where the plan is too long to read in the session. Implementers apply the corpus deltas and write the code.
