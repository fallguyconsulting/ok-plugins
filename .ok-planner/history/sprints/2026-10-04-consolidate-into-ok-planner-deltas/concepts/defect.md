# Defect

## What it is

A defect is a harm the project's rules already decide: the accept list
names it, directly or through a rule it points to, or, while a sprint
is certified, the sprint promises otherwise. The same rule decides what
fixing it means. A matter the rules leave open is not a
defect but an issue for the owner's judgment (see also: issue). A
defect filed for a later run is still a defect.

## Purpose

Because the rule that names a defect also decides its fix, a defect
needs a worker, never a ruling. That lets a run fix what it finds
without asking the owner, and lets every way of finding a defect feed
one list.

## Boundaries

A defect sits at a named site, and it states its harm in the terms of
the rule that decides it. Outside a sprint's certification, a site the
accept list leaves standing is not a defect, whatever its shape (see
also: accept-list). A site where the
rule leaves two compliant forms is a question, not a defect. A defect filed for a later run changes where it waits, not what it
is. A defect whose fix the rules stop deciding is no longer a defect
but an issue for the owner's judgment (see also: issue). Whether a fix may change what a user across
a release boundary observes is the boundary's question, not the
defect's (see also: release-boundary). See also: practice;
practice-violations-are-defects under decisions.
