# The suite owns whole files, and changes a person's file only to retire what an earlier release left

## Choice

The suite's machinery — the front door's administration and ok-planner's true-up core — owns whole files only: version-stamped — save for a fixed-content file, whose bytes never vary across suite versions and which carries no stamp to verify by — deterministically regenerable, overwritten wholesale. True-up rewrites a suite-owned file that carries its stamp or its fixed content with no question.

The estate's layout is the suite's, and true-up brings the whole estate to the current layout on every run the owner lets proceed (see also: skills-read-only-the-current-layout). Of what an earlier release left there, true-up ports what the current skills still use and archives what they no longer use, a project file that collides with a path the suite now writes and a suite file a person edited included. The archive keeps each piece in a folder named as the content was. Among the project's files, true-up removes outright only a file git can recover: a suite-owned file, or a retired family's state file, such as its profile or its baseline, once nothing reads it after the true-up, even where the owner edited it. A state file a kept script still reads stays. Content the suite keeps under the estate's machine-local, git-ignored folder is not the project's work, and true-up deletes the suite's retired machine-local content outright. Any other file true-up would remove that git cannot restore as it stands — one with an uncommitted or staged-only change, or a symbolic link in its path — moves to the archive instead, so true-up never discards uncommitted work. True-up names each file it removes, archives, or rewrites outside the suite-owned set in its report.

The owner's declarations — the design corpus, the docspecs, the surface intent, the project's configuration, the review configuration, the review facts, and the release boundaries — keep their substance. True-up rewrites or removes a retired key or a retired path in them with no question of its own, and changes nothing else in them. The sections and files a retired artifact layout defined count as such retired content (see also: retired-layout-strips-only-recoverable-files). Where the review facts file does not decode as UTF-8, true-up leaves the file as it stands. It files an intake issue that names the file, says that true-up cannot read or rewrite it, and names the retired review tool's path and the path that replaces it, and its report says that it filed one.

A line in a tracked project file, other than a record and the consumer's own rules file and memory file, that names a retired suite script's path behind a prefix that names the project root with certainty is retired content too (see also: retired-script-repoint-needs-a-proven-root). Where the suite's current copy behaves as the retired one did, true-up rewrites the line to name it and names each rewritten file in its report. Where it does not, or where the line sits in the rules file or the memory file, true-up files an intake issue for the owner and leaves the line. True-up removes a retired script once no tracked file other than a record names it.

A line the suite itself wrote into a project document under a retired verb, such as a provenance stamp, is retired suite content, and true-up deletes that line and leaves the rest of the document.

Records are where the ownership rule stops. The estate preserves them indefinitely. True-up moves them and never rewrites their bodies, save a live sprint's retired boilerplate (see also: live-sprints-brought-current-on-true-up), and an archived record keeps the wording it closed with. A discovery run's notes are records wherever they sit, beside the design catalogs or in the archive.

The consumer's own rules file and memory file are categorically untouchable. Where either names a retired suite path or name, true-up names the line and what the current version names in its place, and the owner rewords it. A hand-written overlap, or preexisting guidance the suite would now govern, reaches the owner the same way. Owner-declared configuration takes a new value, and the project's committed harness settings take hook wiring, only as transcription of the owner's explicit answer, save the retired keys and paths above.

Ownership decides which steps wait for the owner's word. A step that deletes a file, moves a file into the archive, or rewrites a file a person edited waits for the one consent the front door asks before any write; every other step runs on the invocation alone. The questions that ask the owner for input come after the plan runs (see also: true-up-asks-once-before-destructive-steps, administration-is-a-user-act).

## Rationale

Whole-file ownership is what makes a silent true-up safe and drift correction trivial — overwrite, never merge. The moment the machinery edits shared files it needs merge logic, risks destroying human work, and loses the ability to regenerate its layer deterministically. The estate's layout is the suite's because the current skills read only the current layout: content an earlier release left behind either serves in its current place and form or misleads every skill that meets it. Archiving rather than deleting keeps the owner's work: git keeps every committed file a removal takes, and the archive keeps every file git cannot restore. The suite's machine-local content is state the suite's own tools wrote, so a retired piece of it holds no work of the owner's. The owner's declarations state the owner's intent, so true-up changes no substance in them; a retired key or path names the suite's own layout, which the suite may move. A line the suite wrote into a project document under a retired verb is the suite's own text, so deleting it removes nothing the owner wrote. A retired family's state file configured a family that no longer runs, so nothing the owner relies on reads it, and version history keeps whatever the owner added. A line naming a retired suite script points at the suite's own layout; repointing it to a copy that behaves the same changes nothing the caller relies on, and a caller whose behavior would change reaches the owner as an issue rather than as unrecorded work. A review facts file that does not decode reaches the owner the same way, since true-up cannot rewrite it with certainty, and the issue keeps one shape for every retired reference true-up cannot rewrite. A record states what was true when it was written, so rewriting one to match a current layout destroys the only thing it is for. The consumer's rules file and memory file carry the owner's own instructions to every session, so the suite asks the owner to reword them rather than merging its text into theirs.

## Alternatives

- Managed sections inside shared files — merge logic, marker rot, and inevitable collisions with human edits.
- Silent adoption of overlapping preexisting files — the machinery destroys or shadows guidance the project chose deliberately.
- Leave a collision, or a person's edited copy of a suite file, in place for the owner to settle — the estate stays partly on a retired layout that no current skill reads.
- Delete what the current skills no longer use, whatever its git state — work git cannot restore is lost.
- Rewrite the retired review tool's name byte for byte in a review facts file that does not decode — a second idiom beside the rule that true-up never rewrites an undecodable file, and a wrong edit in an encoding where those bytes do not stand for the name.
- Report an undecodable review facts file on every run, with no write and no issue — a notice the owner must act on unprompted, which every true-up repeats and nothing records.
