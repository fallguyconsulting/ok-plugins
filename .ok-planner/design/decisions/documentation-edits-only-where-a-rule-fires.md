# A documentation run edits a file only where a rule fires

## Choice

A documentation sprint's writer edits a file only where one of a fixed
set of rules fires, and every edit names its rule: a claim is false
against the tree; a public element of a listed class is missing; an
element the surface intent keeps internal appears; a sprint closed
since the stamp changed what a user can do and the text does not say
so; the file departs from its docspec's shape or layout; the file
departs from its docspec's reader or coverage, because it addresses
another reader, covers what the docspec leaves out, or omits what the
docspec covers; or a claim the tree cannot settle stands. Where a file
departs from its docspec's reader or coverage, the writer rewrites the
passage that departs. Every other sentence stays as written. A file
the docspec's layout calls for and the tree lacks is written whole.

## Rationale

A run that may improve any sentence improves a few every time, and
documentation churns with no change in the product. Naming the rule
on each edit makes the run's change list short enough for the owner to
read, and lets the owner see why each sentence moved. The reader and
coverage rule rests on a judgment of what departs, and a run that
reaches a changed docspec rewrites more prose under it; without the
rule, documentation never follows the owner's change to whom it is
for or what it covers.

## Alternatives

- Hold a file only to its docspec's shape and layout — fewer
  rewrites, and a change to the docspec's reader or coverage never
  reaches the documentation.

- Rewrite each reached file whole — always consistent, and every run
  churns text no change touched.
- Let the writer improve any sentence it judges weak — the prose
  improves over runs, and no edit can be traced to a change in the
  product.
