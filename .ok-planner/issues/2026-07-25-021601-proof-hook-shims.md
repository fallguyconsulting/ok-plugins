# Hook-shim conformance has no mechanical check

## Problem

The contract states the shim conformance test in prose ('the shim may read nothing but the path it execs') but nothing fails when a plugin-root hook grows behavior.

## Candidates

- Amend decision:hook-shims Proof to name a shim-shape conformance check once one exists
- Record the choice as prose-governed in the decision and retire the proof expectation

## Discussion

**The question.** `decision:hook-shims` requires (per `decision-artifact`'s
invariants) a mechanical check that fails if the choice is silently
violated. No such check exists — the decision's own Proof section admits
this in prose. Should the decision commit to eventually building one, or
should it be revised to declare the guarantee permanently prose-only?

**Where this comes from, re-verified against current code.** This issue
was originally filed to the legacy `issues.jsonl` (row `proof-hook-shims`,
now archived at `.ok-planner/history/issues.jsonl:3`) and converted
verbatim into this file by the intake migration — its Problem text is
unchanged and still accurate. Today the plugin-root hook files are:
`plugins/ok-planner/hooks/session-start`, `plugins/ok-planner/hooks/user-prompt-submit`,
and `plugins/ok-plumbline/hooks/post-edit.js`. Each is a thin shim: resolve
the project root by walking up for `.git`, then either `exec` (bash) or
`spawnSync` (Node) the same-named file under the project's materialized
estate (`.ok-planner/hooks/...` or `.ok-plumbline/hooks/...`), exiting/passing
silently when that file is absent. None reads any plugin-root content beyond
its own exec path, so the shim shape holds today — but nothing in the repo
would catch it if one grew behavior. A repo-wide search found no lint rule,
fixture test, or CI step that inspects hook-file shape at all (ok-plumbline's
own `true-up` diagnostic only checks whether the materialized copy exists
and is version-current, not what the plugin-root shim itself contains). None
of the three shim files carries a `@decision:hook-shims` annotation either,
consistent with there being no enforcing artifact yet to annotate.

**What the corpus says.** No artifact decides the outcome; several describe
the mechanism that produced this issue and the standard any future check
would have to meet:

- `decision-artifact`'s invariants: "The proof field is mandatory: a
  decision for which no violation-detecting check can be named is either a
  default (delete it) or an unenforced intention (an issue is filed for
  owner calibration)." This is exactly what happened — the current state
  (decision kept, issue filed) is the corpus's prescribed *process*, not a
  defect in it. It doesn't say which of the two outcomes (build the check,
  or drop the expectation) the owner should pick.
- The `{{DECISION-DEFINITION}}` token in `skills/_shared/artifact-definitions.md`
  echoes the same framing: an unenforced intention is filed "for owner
  calibration — the next sprint decides whether to make it enforceable or
  let it go," explicitly naming both outcomes as live options without
  favoring either.
- `{{PROOF-PROTECTION-RULE}}` sets the bar any new check would have to
  clear to count as non-vacuous: a concretely producible falsifier — some
  mutation (a shim reading beyond its exec path, or a shim growing real
  behavior) that must turn the check red, with the check green again once
  reverted.
- `materialized-artifact` states shims are "deliberately not behavior"
  handled by `hook-shims`, but defines no check of its own.
- `decision:edit-hook-blocks-in-turn` is a close precedent already in the
  live corpus: its Proof section is also partially met ("The lint binary's
  violation exit code... is asserted by the fixture test suite... The hook
  wiring itself (change-scoping, fail-open paths) has no automated check;
  that gap is filed to the intake queue.") — i.e. a decision can carry a
  proof that is real for part of the choice and prose-only for the rest,
  with the gap deferred to intake, and that has not been treated as
  disqualifying elsewhere in the corpus.

**What the candidates would mean.**

- *Amend the Proof to name a shim-shape conformance check once one
  exists* commits the project to eventually building a mechanical check.
  One buildable shape the code surface suggests (not proposed as the
  answer, just what's technically available): a fixture/golden-file test
  per plugin asserting each `hooks/<name>` file matches a known-good
  template for its language (bash vs. Node) parameterized only by the
  hook name — any hand-added logic would diverge from the template and
  redden the check. This satisfies `{{PROOF-PROTECTION-RULE}}`'s
  falsifier bar. Cost: someone has to build and maintain that fixture
  across every plugin's hook set, and keep it in sync as new plugins add
  hooks.
- *Record the choice as prose-governed and retire the proof expectation*
  removes the obligation, but as stated it sits awkwardly against
  `decision-artifact`'s own invariant, which recognizes only two
  permanent states for a decision: a default (no real alternative — but
  `hook-shims` clearly has one, per its own Alternatives section) or an
  unenforced intention with an issue filed for owner calibration (which
  is the transient state the corpus already has it in, not a terminal
  one). Taking this candidate as written would either need
  `decision-artifact`'s invariant itself amended to recognize a third,
  permanent "prose-only, no check ever expected" category, or would leave
  `hook-shims` in a state the concept's own compliance bar doesn't
  currently accommodate.

**What the ruling needs to decide.**
1. Does `decision:hook-shims` commit to a mechanical shim-conformance
   check (and what must it catch), or does its Proof section change to
   state the guarantee is prose-only with no check ever expected?
2. If prose-only: does `decision-artifact`'s proof invariant need
   amending to recognize a permanent unenforced-decision category, or is
   leaving `hook-shims` as a standing, never-closed calibration item
   acceptable as-is?
